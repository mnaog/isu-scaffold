# LithosAIとOpenCodeの実タスク所要時間

2026年10月1日、このMacからDeepSeek V4.1 FlashでRustのバグ修正を測定した。追加した4プラン比較では、**起動済みOpenCodeへの依頼から修正・テスト・最終回答までの中央値は、無印11.35秒、Fast17.04秒、Ultra10.93秒、Ultra Chat7.39秒だった。全12試行で修正と独立テストに合格した。**

**無印とUltraは、この小タスクの完了時間では約4%の差しかなかった。Fastの優位は見られず、速度最優先なら引き続きUltra Chatを第一候補とする。** ただし各3回の小規模測定であり、同等性能の証明や長い推論での生成速度比較ではない。

## 無印とFastを追加した同時比較

同じRust課題、max推論設定、起動済みOpenCode、直結で、4プランを各3回実行した。前回のUltraの数値との単純比較では時間帯の差が入るため、UltraとUltra Chatも同じバッチ内で測り直した。順番は無印→Ultra→Fast→Ultra Chatを基本とし、ラウンドごとに先頭を1つずつずらした。

| 経路 | 1回目 | 2回目 | 3回目 | 中央値 | 成功 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 無印 | 13.75秒 | 11.13秒 | 11.35秒 | **11.35秒** | 3/3 |
| Fast | 17.04秒 | 12.22秒 | 19.16秒 | **17.04秒** | 3/3 |
| Ultra | 11.41秒 | 9.79秒 | 10.93秒 | **10.93秒** | 3/3 |
| Ultra Chat | 7.39秒 | 7.37秒 | 7.43秒 | **7.39秒** | 3/3 |

無印のモデルIDは `deepseek-ai/DeepSeek-V4.1-Flash`、Fastは `deepseek-ai/DeepSeek-V4.1-Flash-fast`。公開モデル一覧で利用可能なことを確認してから実行した。

無印に対してUltraが短縮した時間は中央値で約0.43秒、約3.8%だった。「無印とUltraはほぼ同じかもしれない」という話には、この課題では整合する。ただし無印の範囲は11.13〜13.75秒、Ultraは9.79〜11.41秒で、3試行だけでは統計的な同等性までは示せない。Fastは12.22〜19.16秒とばらつき、今回の待ち時間を短縮する選択肢にはならなかった。Ultra Chatは7.37〜7.43秒で、無印より約35%、Ultraより約32%短時間だった。

各タスクのモデル応答数は無印5〜6回、Fast6回、Ultra5〜7回、Ultra Chat5〜6回。長い回答を連続生成する負荷ではなく、読み取り・修正・テストを挟む短い呼び出しの積み重ねである。この結果から、各プランの長文生成token/sまで同じとは言えない。混雑・キャッシュ・推論量・経路による遅延の原因も分離していない。

### 計測用の権限制限を補正した理由

追加比較の最初の12試行では、実験側が許可していなかった `cat`、`head`、`tail` により、無印2回目・3回目、Fast2回目、Ultra Chat3回目でツールが拒否された。これはプランの速度ではなく計測条件が作った余計なやり直しなので、上表には採用していない。

通常の読み取り操作を全プランで同じように許可して12試行を取り直した。最終比較ではツールの権限拒否は0件。元の公開8テストと、300通りの参照比較・整数上下限を含む独立2テストに全試行が合格した。初回の制限付き記録も `.local/lithos-ultra/task-results-tiers/` に残し、取り直しで結果を隠さないようにした。

前回報告のUltra3回目にも `cat` の拒否が1回あったことが、今回の精査で判明した。前回の12.52秒にはそのやり直しが含まれるため、今回の4プラン比較を優先する。前回の中央値10.10秒自体はその試行ではなかったが、前回の記録も完全に制約のない動作ではなかったことを補足する。

追加比較の[集計データ](lithos-opencode-tiers-20261001.json)と、`.local/lithos-ultra/task-results-tiers-v2/` にある生成コード・会話・テスト結果を保存した。実験コードは `.local/lithos-ultra/task-bench-tiers-v2.py`。SHA256 `75e389f198b71c8f9509f6ecbdc29fcc5444736d088a28b92de790182b1d7a0f`。

測定中はグローバル設定とデフォルトモデルを変更していない。測定後、ユーザーの指定により通常利用とscoutをLithos無印に統一した（[現在の設定](../roles/opencode-lithos.md)）。以下は初回のZenを含む測定と共通の方法論であり、追加比較とは別バッチの結果として読む。

## 初回のUltraとZenの比較


| 経路 | 1回目 | 2回目 | 3回目 | 中央値 | 成功 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Lithos Ultra Chat | 7.41秒 | 7.13秒 | 7.54秒 | **7.41秒** | 3/3 |
| Lithos Ultra | 10.07秒 | 10.10秒 | 12.52秒 | **10.10秒** | 3/3 |
| OpenCode Zen 従量課金 | 22.80秒 | 34.84秒 | 61.51秒 | **34.84秒** | 3/3 |

ZenはGoではなく、通常の `https://opencode.ai/zen/v1` を使用した。モデルIDはUltraが `deepseek-ai/DeepSeek-V4.1-Flash-ultra`、Ultra Chatが `deepseek-ai/DeepSeek-V4.1-Flash-ultra-chat`、Zenが `deepseek-v4.1-flash`。

OpenCode 1.18.34のサーバーを一度起動し、セッション作成とprovider情報の読み込みを済ませてから計時した。HTTPの依頼送信直前から、OpenCodeが最終回答を返すまでを単調増加時計で測った。CLI起動・サーバー起動・終了処理・実験側の独立検証は含まない。OpenCodeによるファイル読み取り、推論、編集、テスト、最終回答は含む。これはユーザーの求める「待ち時間」に近い値である。

## 課題と正しさの確認

外部依存のない小さなRust crateを一時ディレクトリへ用意した。元の関数は約15行で、整数の閉区間を正規化するもの。隣接区間の結合、包含区間の扱い、逆転区間の除外、i64上限でのオーバーフローに不具合がある。READMEに仕様、公開テストに8ケースを用意した。

全試行へ同じ依頼を送った。

> Read README.md and src/lib.rs, run cargo test --offline to reproduce the failures, fix normalize in src/lib.rs, then run cargo test --offline again. Do not modify existing tests or Cargo.toml. Do not install dependencies, use the network, create subagents, or commit. Work only in this project. Finish with a concise summary of the fix and test result.

各回、初期ソースと公開テストを復元し、新しい会話で開始した。ビルド成果物は再利用した。初回比較では全9回でテストの失敗再現・コード編集・再テストが行われた。既存テストとCargo.tomlが変更されていないことを実験側で確認した。

最終回答のあと、実験側からさらに2つの独立テストを追加して実行した。300通りの決定的な乱数ケースを、整数集合から作る参照実装と照合し、i64の上下限も検査した。元の8テストと合わせて全試行が合格した。モデルの「テストが通った」という申告だけを成功判定には使っていない。

ISUCONの配布アプリやベンチマーカーは対象にしていない。remote変更、deploy、共有ベンチは実行していない。

## どこで時間が違ったか

| 経路 | ツール実行区間の中央値 | それ以外の時間の中央値 | 各試行のモデル応答数 |
| --- | ---: | ---: | --- |
| Ultra Chat | 3.69秒 | 3.52秒 | 6 / 5 / 6 |
| Ultra | 3.64秒 | 6.74秒 | 5 / 6 / 8 |
| Zen | 3.69秒 | 31.08秒 | 5 / 7 / 6 |

ツール時間はOpenCodeに記録された開始・終了時刻から区間の和集合を取り、並列実行を二重加算しないようにした。「それ以外」は各試行の総時間からツール区間を引いた値で、API待ち、通信、推論、OpenCodeの内部処理を含む。GPUの計算時間そのものではない。また、それぞれ独立に中央値を取っているため、表の列を足しても総時間の中央値と一致するとは限らない。

ツールにかかる時間はほぼ同じで、差は主にツールの外側に出た。ただし行動も完全には一致しない。Ultraの3回目は8応答・10ツールへ増えた。Zenの2回目は `ls -R .` でビルド成果物も列挙し、入力が約38kトークンへ増えた。他の試行は約5.3k〜9.4kだった。この違いも実際の作業時間の一部だが、**79%短縮を配信システムだけの効果とは解釈できない**。Zenの3回目は入力約8.5k、6応答でも61.51秒かかっており、長い入力だけが遅延の説明ではない。

## 推論設定とUltra Chatの注意点

比較には同じOpenAI互換アダプターとモデル能力設定を使い、`reasoningEffort: "max"`、reasoning対応、`reasoning_content`の継続を明示した。計測用のローカル上限はcontext 131072、output 8192で、サービスが提供する最大値を表すものではない。推論の呼び出し以外の外部ネットワーク利用・subagent・不要なツールを無効にし、Rustの言語サーバーと外部プラグインも無効にした。

補助測定で送信HTTPを観測し、3経路とも `reasoning_effort: "max"` が送られることを確認した。直結測定でも同じモデル設定を使用し、全経路の応答に推論テキストがあることを確認した。

重要な違いとして、Ultraは推論トークン数を `usage.completion_tokens_details.reasoning_tokens` に返し、Ultra Chatは `usage.reasoning_tokens` に返していた。OpenCodeの直結記録ではUltra Chatのreasoning token数が0になるが、各試行に1313〜2122文字の推論テキストが記録されている。補助測定でもUltra Chatは602 / 966 / 628 reasoning tokensを返した。**「Ultra Chatは推論しないから速い」という説明は、この実測とは合わない。**

この返却形式の差により、OpenCodeの表示上のreasoning token数や出力token数をそのまま経路間比較すると誤る可能性がある。今回の採否判断はトークン速度ではなく、修正品質と総完了時間を中心にした。

## 補助測定と測定器の影響

API呼び出しの内訳を調べるため、初めはローカルのHTTP中継を入れた。この中継は上流接続を毎回新しく作る実装であり、通常のOpenCodeの接続再利用と異なる。したがって、その総時間を最終的な実用値としては採用しなかった。

| 経路 | 中継ありタスク中央値 | 1 API呼び出し中央値 | 最初の出力deltaまでの中央値 |
| --- | ---: | ---: | ---: |
| Ultra Chat | 11.07秒 | 1.06秒 | 0.86秒 |
| Ultra | 13.41秒 | 1.48秒 | 1.27秒 |
| Zen | 27.46秒 | 2.43秒 | 1.30秒 |

この表と直結測定は別の実行であり、経路ごとの混雑・推論量・行動も変わっている。差をそのまま「中継のオーバーヘッド」として差し引くことはできない。特にZenは後の直結測定の方が遅い試行もあり、接続再利用だけでは説明できない。

最初の中継実装はPython既定のUser-AgentでZenから403を受けた。OpenCode側のUser-Agentを引き継ぐように直してから3回の正常測定を行った。これら初期の403は測定器の接続問題として扱い、モデルの速度や信頼性の比較へは入れていない。

前段の単純出力測定では、Ultraへ整数1〜200の列挙を依頼し、400出力トークンを受信した。API直接の中央値は最初の出力まで1.06秒、受信完了まで1.42秒、最初と最後の出力の間は約0.36秒だった。推論トークンは0。約770〜1134 token/sという見かけの速度は単純な数列・チャンク受信からの計算で、通常のコード生成速度を保証しない。

前段で示したOpenCodeの `step_start` → `step_finish` 約0.53秒も、最初の出力待ちを含まない。依頼全体の処理時間には使わない。本レポートの主結果は冒頭の直結・起動除外測定である。

## 提示された会話への評価と採用判断

「token/sより、依頼を終えるまでのwall-clock timeを見る」という方針は妥当であり、今回の実タスクでもLithosの価値を確認できた。性能を試すために導入したのであれば、**この結果ではUltra Chatを普段使いの第一候補、Ultraを比較用の候補にする**という判断になる。追加料金の議論より、この課題で約7秒で正しく終わったという結果を重視する。

ただし、提示された会話中のArtificial Analysisの具体的な数値や「公式3.7秒/step」などは、本調査で原データまで再確認できていない。本レポートの実測と混ぜて再利用しない。「DeepSeek公式に対して3倍以上」「全providerの中で最速」「100kコンテキストでも同じ倍率」とは結論しない。公式APIのキーを今回使用していないため、公式との比較は未実施である。

Ultra Chatの高速化の仕組みや、Ultraと品質が完全に等しいことも、この小課題だけでは分からない。3回ずつの結果からp95、長期の稼働率、大規模並列時の安定性は推定できない。初回比較の9試行では完了失敗はなかったが、直結時のHTTP再試行回数は計測していない。

入力条件は小さく、既知の失敗テストがある修正課題である。大規模な調査、100k〜500kの会話、長い推論、キャッシュが冷えた状態、複数セッション並列では結果が変わり得る。実運用の採用はまず小規模で始め、難しい課題では品質と再試行も観察するのが妥当である。

測定中のデフォルトはUltraで、今回のmax設定とUltra Chat登録は実験プロセス内だけに適用した。測定後のデフォルトはユーザー指定により無印へ変更した。以前の最小接続設定を、そのまま今回のmax設定と同一だとは扱わない。
