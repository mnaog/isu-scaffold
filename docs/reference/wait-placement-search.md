# wait設置探索

特定の処理へ小さな待ち時間（wait）を入れてスコアを伸ばせる場所を、ベンチマーカーの中を見ずに探す手順と、その効果・限界の考察。

サーバーの資源が飽和していないのにスコアが頭打ちになったとき（Phase 2の後半）に使う。根拠にしてよいのは、公開された当日マニュアルとアプリケーションマニュアル、サーバー側の観測（アクセスログ、各nodeの計測）、ベンチマーカーが選手向けに出す出力（score、エラー）だけとする。ベンチマーカーのソース、bench node上の計測、選手に見えない`[ADMIN]`ログは使わない。

## 背景: 練習で起きたこと

| 練習 | 入れたwait | 結果 | 判断の根拠 |
| --- | --- | --- | --- |
| ISUCON13 | 状態を変えないdummy moderateを1,000ms、moderator入口の`GET /api/livestream`を50ms | OFF 861,717 → ON 978,554 / 986,591 / 980,081（中央値+13.7%）。dummy moderateは7,791回→中央値63回、完走viewerは4,404→4,979 | ベンチマーカーのソース、他チームの参加記 |
| ISUCON13 | 上の2定数を10走で探索 | 0/0は878,052。200〜500ms、500〜5,000msの広い範囲が台地で、採用値500/2,000msは1,043,983。同条件2走の差は約0.8% | 選手向けの出力とサーバー側の件数 |
| ISUCON13 | 予約の空き枠競合の400だけ100ms | 1,108,861 → 1,117,031。予約成功1,372は維持、競合失敗6,101→466 | サーバー側の件数 |
| ISUCON13 | icon更新の流量上限を65→75 RPS（waitを弱めた） | icon更新の完了+12%、完走viewer-1.9%、score-1.66% | サーバー側の件数 |
| ISUCON13 | 長時間配信の予約を最大15秒待たせる | 予約成功1,372→6、完走viewer 5,124→563、score 約100.9万→約9.0万 | サーバー側の件数 |
| ISUCON12本選 | ログインを130ms | 647,375 → 653,245（+0.9%、判定不能） | ベンチマーカーのソースと`[ADMIN]`ログ |
| ISUCON12本選 | ログインの遅延100→0ms（waitを外した） | 1,214,189 → 1,286,199（+5.9%）。`POST /login`は12,931→37,024件 | サーバー側の件数 |

大きく伸びたwaitは、ベンチマーカーの中の情報から見つけていた。一方で、waitは外れると大きく損をする（予約の15秒）し、得点する処理に入れると伸びない（ISUCON12のログインは、当日マニュアル上1回3点の加点対象だった）。

## 考え方

ベンチマーカーの多くは、処理が終わると同じシナリオをすぐに次の周回へ入れる。この場合、ある処理を速くすると、その周回が増えて資源（サーバーのCPUや接続、ベンチマーカー側の並列枠やCPU）を使う。得点しない周回が増えれば、得点する周回から資源を奪う。

waitが効くのは、**得点しない周回の回転を落とし、空いた資源が得点する周回へ回る**ときだけである。得点する周回、または得点する周回の前提になる処理（ログイン、登録、予約など）に入れれば、得点が減る。

## 手順

### 1. 公開資料で処理を3つに分ける

当日マニュアルの得点計算とアプリケーションマニュアルから、エンドポイントを分類し、表にしてリポジトリへ残す。

| 分類 | 意味 | wait |
| --- | --- | --- |
| 得点 | 成功すると加点される | 入れない |
| 前提 | 得点する処理へ進むために必要（ログイン、登録、予約、入場など） | 原則入れない |
| 無得点 | 加点されず、得点する処理にも必要ない（検索、一覧、管理操作、失敗が確定した処理など） | 候補 |

ISUCON12本選のように1回ごとの配点が表で示される場合は、配点をそのまま使う。ISUCON13のように「投げ銭の合計」とだけ書かれる場合は、得点に至るまでの経路をアプリケーションマニュアルから読み、前提を広めに取る。分類に迷うものは「前提」に入れる。

### 2. 周回を数える

アクセスログをsession単位でつなぎ、分類ごとの件数と周回の回転を出す。初動のAnsibleで入れるLTSVログにはsession（`observability_nginx_session_source`）が入っている。初回の`isuscope survey-run`で記録する行動遷移も使う。

1分あたりで次を出す。

- 分類ごとの成功件数（得点・前提・無得点）
- 無得点の処理だけを繰り返すsessionの数と、1sessionあたりの周回数
- 得点の処理の成功件数と応答時間

同じ時間帯にサーバーの資源が飽和していないことも確認する。飽和しているなら、先にそこを直す。

### 3. 候補を選ぶ

次をすべて満たすものを候補にする。

- 「無得点」に分類される
- 件数が得点の処理と同じ桁以上ある、または周回が速すぎる（1sessionが同じ処理を短い間隔で繰り返す）
- 遅らせても整合性や応答の内容が変わらない（状態を変える処理は、状態を確定させてから待つ）
- 待ち時間がタイムアウトより十分短い

失敗が確定した応答（在庫切れ、枠の競合など）も候補になる。成功する処理や入力不正は遅らせない。

### 4. 探りのwaitを1つだけ入れる

候補を1クラスだけ選び、50〜100ms程度のwaitを環境変数で切り替えられる形で入れる。isuscopeの`run`を1回回し、直前の基準runと比べる。

```bash
isuscope run --hypothesis "無得点の<処理>に50msのwaitを入れる。base <run>では<処理>が毎分N件で、得点の<処理>と資源を分け合っている。<処理>の件数が減り、得点の<処理>の成功件数が増える"
isuscope query latest --base <base-run> --view http --label route=<得点の処理>
isuscope query latest --base <base-run> --view http --label route=<候補の処理>
```

判定はscoreだけで行わず、サーバー側の件数で行う。

| 観測 | 判定 |
| --- | --- |
| 候補の件数が減り、得点の処理の成功件数が誤差を超えて増えた | 効いている。値の探索へ進む |
| 候補の件数が減ったが、得点の処理の件数は変わらない | 資源を分け合っていない。waitを外す |
| 得点または前提の処理の件数も減った | 候補が前提を含んでいた。waitを外し、分類を見直す |
| エラー、タイムアウト、整合性チェックの失敗が出た | 即座に外す |

誤差の幅は、同じ構成で回したrunの差から見積もる。練習では同条件の差が約1〜2%、EC2の停止・起動を挟むと同じ配布内容で-7.3%だった。環境が変わったら基準runを取り直す。

### 5. 値を決める

効いたwaitだけ、値を粗く数点振る（例: 50、200、500、2,000ms）。二分探索はしない。効果は単調とは限らず、台地になることが多い。台地の中で、再走しても落ちない値を選ぶ。

アーキテクチャを大きく変えると最適な値は変わるので、最終構成が固まった後にもう一度粗く確認する。

### 6. 条件付きにする

固定値のwaitは、ベンチの負荷が練習と違うと損になる。可能なら、得点の処理の待ち行列や応答時間が悪化したときだけ無得点の処理を遅らせる形にする。少なくとも環境変数で即座にOFFへ戻せるようにし、deployで既定値に戻らないことを`isuscope`のrunの記録（仮説・分析）で確認する。

## 期待される効果

- **サーバーを速くしても伸びない局面を動かせる。** ISUCON13では、CPU 40〜50%で飽和がないまま50回ベンチを回して+2.5%しか伸びなかった区間を、waitで+13.7%動かした。
- **安く、戻しやすい。** 数行のコードと環境変数で入れられ、外すのも一瞬で済む。構成変更の前に試せる。
- **ベンチマーカーの中を見る代わりになる。** 周回を数え、1つずつ遅らせて得点処理の件数を見ることで、「どのシナリオが資源を奪っているか」を外側から実験で確かめられる。
- **ついでに得点構造の理解が深まる。** 探りのwaitの結果は、分類表が合っているかの検証にもなる。外れた候補は、前提の処理を見落としていた印になる。

## 限界

- **仕組みまでは分からない。** 探りのwaitは「効いた・効かない」を教えるが、奪い合っているのがサーバーの資源なのか、ベンチマーカー側の並列枠やCPUなのかは分からない。そのため、効いた理由から次の手を類推しにくい。
- **公開資料の得点定義が粗いと分類を誤る。** 配点が表になっていない問題では、完走や最終段階でまとめて加点される構造を見落とし、前提の処理を無得点に入れる危険がある。予約を15秒待たせた例のように、前提を詰まらせると大きく落ちる。
- **得点の処理の件数は代理指標である。** 1件あたりの点数が一定でない問題（投げ銭の額が変わるなど）では、件数が増えてもscoreが増えないことがある。
- **小さな効果は誤差に埋もれる。** 1回ずつのrunでは1〜2%の差を判定できない。探りのwaitで見るべきなのは、scoreより件数の変化の方向である。
- **値は練習のベンチに過剰適合しやすい。** ベンチマーカーの版、並列度、データ量が変われば最適な値も変わる。練習中にベンチマーカーが変わり、アプリを変えずにscoreが+18%動いたこともある。追試で同じ値が効く保証はない。
- **規約とタイムアウトの確認が必要である。** 意図的な遅延、429などの応答の変更、状態を変える処理の遅延が仕様違反や減点にならないかを、当日マニュアルとアプリケーションマニュアルで確かめてから入れる。waitはタイムアウトより十分短くする。
- **waitの外し忘れ・戻り忘れが起きやすい。** 環境変数の読み込み不具合でOFFのつもりがONだったこと、deployで既定値に戻り気づかないまま4回ベンチを回したことがある。
