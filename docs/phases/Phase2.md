# Phase 2: アーキテクチャを変えて徹底的に改善する

## 目的

Phase 1で初動と並行して自明な無駄を解消した構成を土台に、キャッシュ、メモリ化、非同期化、複数台構成などを導入し、ベンチマーク全体のスコアを徹底的に伸ばす。

このPhaseでは、個々のAPIを均等に高速化するのではなく、得点へ直接つながる処理を優先し、シナリオ全体として最も高いスコアを出せる構成を目指す。

## 基本方針

- ベンチマークシナリオと得点構造を判断の基準にする
- スコアへ直接つながる処理へ資源を集中する
- 高速化によって負荷だけが増える処理にも注意する
- キャッシュやアーキテクチャ変更を含め、必要な手法を制限しない
- スコアだけでなく、処理件数、失敗率、レイテンシー、CPU、I/Oを確認する
- 大きな変更でも、ローカルのコードと設定を正とする
- 有効な構成をコミットし、戻せる地点を残す
- 公式仕様、整合性条件、失格条件を常に守る

## 得点経路へ資源を集中する

Phase 1で整理したシナリオを基に、得点を生む処理と、負荷だけを増やす可能性がある処理を区別する。

- 得点へ直接つながる処理の完走率を上げる
- 重要な処理の待ち時間と競合を減らす
- DB接続、CPU、I/O、ネットワークの配分を見直す
- 高速化によって低優先シナリオの実行回数だけが増えていないか確認する
- エラー数だけでなく、シナリオごとの成功数と得点を見る

## アプリケーションとデータ経路を変える

必要に応じて次の手法を使う。

- アプリケーションキャッシュ
- データのメモリ保持
- レスポンスや完成済みJSONのキャッシュ
- 事前計算と集約結果の保持
- write-behind
- 非同期処理
- バッチ化
- 不要な永続化や外部通信の削減
- 静的ファイルや画像配信の最適化
- ETagや条件付きレスポンス

キャッシュやメモリ化では、データの正本、更新方法、無効化条件、initialize後の再構築方法を明確にする。

## 複数台構成を利用する

計測結果とシナリオの性質に基づいて各サーバーの役割を決める。

- Web、アプリ、DB、DNS、バッチなどの分離
- nginxなどによるリクエストの振り分け
- 読み取り処理と書き込み処理の分離
- データや利用者単位の分割
- CPU負荷、I/O負荷、接続数の分散
- サーバーごとのプロセス数と資源配分の調整

台数があるという理由だけで分割せず、競合を減らし、得点経路の処理能力を上げられる構成にする。

## 流量と優先度を制御する

計測で必要性が確認できた場合は、Admission Controlや流量制御も利用する。

- 得点へ直接つながる処理を優先する
- 低優先処理がCPUやDB接続を占有しないようにする
- 同時実行数、キュー、タイムアウトを調整する
- nginxやアプリケーションで処理経路ごとの制御を行う
- 制御によって整合性エラーや失格条件を発生させない

単純にリクエストを拒否することを目的とせず、ベンチマーク全体を安定して完走させ、得点を最大化するために使う。

## 改善サイクル

大きな構成変更でも、計測には通常の`isuscope run`を使う。`isuscope brief latest`で全体を確認し、変更前のrunを`isuscope query latest --base BASE_RUN ...`へ指定して仮説対象を比較する。採否は対象runへ`isuscope analyze RUN_ID ...`で記録する。

```text
isuscopeで現在の制約を確認する
→ 得点への影響を考える
→ 改善方針を決める
→ 実装と構成を変更する
→ コマンドでデプロイする
→ ベンチマークを実行する
→ スコアとシナリオ別結果を分析する
→ 採用、修正、または元へ戻す
→ コミットする
→ 次の制約へ進む
```

一つの改善によって負荷の位置やシナリオの実行量が変わるため、毎回最新の計測結果から次の改善を判断する。

## 再現性を維持する

- コード、設定、構成定義をローカルリポジトリで管理する
- サーバー上だけに存在する変更を残さない
- デプロイ、再起動、initializeをコマンドから実行できるようにする
- 複数台へ同じ手順で再配置できるようにする
- 大きな変更の前後に戻せるコミットを残す

## Phase 3への移行

終了時刻が近づき、新しい大規模変更よりも最終構成の固定と再現性確認を優先すべき状態になったら、作業中のagent（CodexまたはClaude Code）はPhase 3への移行を提案する。

Phaseの変更は人間が決定する。
