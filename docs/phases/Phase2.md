# Phase 2: 1台構成で自明なボトルネックを一掃する

## 目的

1台構成を維持したまま、インデックス不足、N+1、重複処理などの自明なボトルネックを高速に解消する。

この段階で観測できる負荷は、現在のスコアへすぐ反映されなくても、負荷の増加に伴ってどこかで必ず顕在化すると考える。

複雑な最適化には進まず、安全で効果が明確な改善を短いサイクルで積み重ねる。

## 基本方針

- まずインデックス不足を調査して解消する
- 次にN+1クエリを一掃する
- その後も計測上位の自明な無駄から順番に解消する
- 変更は小さく保ち、すぐにデプロイして計測する
- スコアだけでなく、SQL回数、走査行数、処理時間、CPU、I/Oを見る
- スコアが変わらなくても、処理量が明確に減っていれば将来の余力として評価する
- 正しさを維持し、ベンチマークのエラーを増やさない
- 採用した変更はコミットし、不要な試行は元へ戻す

## 最初に確認するもの

### インデックス

- 高頻度SQLの実行計画
- 全件走査
- 大量の行を読み捨てているSQL
- WHERE、JOIN、ORDER BYに必要なインデックス
- 複合インデックスの列順
- 使用されていない、または重複しているインデックス

インデックスは推測だけで追加せず、実際のSQLと実行計画を確認する。

### N+1

- 一覧の要素ごとに発行されるSQL
- ループ内のユーザーや関連データ取得
- 要素ごとの集計クエリ
- 同じリクエスト内で繰り返される同一SQL
- SQL以外の外部コマンドや外部通信の繰り返し

一括取得、JOIN、GROUP BYなどを使い、処理結果を変えずに呼び出し回数を減らす。

## 改善サイクル

各変更は、仮説付きのrun、前後比較、判定を一単位にする。

```bash
isuscope run --hypothesis "変更理由と改善を期待する観測値"
isuscope brief latest
isuscope query latest --base BASE_RUN --metric-prefix benchmark. --group-by scenario --limit 100
isuscope analyze RUN_ID supported --analysis "観測結果と採否の理由"
```

HTTPやDBの比較は`query --base`へ`--view`、`--source`、`--label`または`--label-contains`、必要なら`--group-by sql-shape`を指定し、仮説の対象だけを取り出す。

```text
isuscopeで現在のボトルネックを確認する
→ 自明な問題を選ぶ
→ 原因と期待する変化を明確にする
→ 必要な変更を実装する
→ コマンドでデプロイする
→ ベンチマークを実行する
→ スコアと内部指標を比較する
→ 採用または元へ戻す
→ コミットする
→ 次のボトルネックを確認する
```

一つの問題を解消すると、次に重い処理が見える。特定の箇所へ固執せず、計測結果に従ってボトルネックを高速に移動していく。

## このPhaseで行わないこと

- アプリケーションキャッシュの導入
- データのメモリ保持
- write-behindや非同期永続化
- サーバー間の役割分担
- データの分割やシャーディング
- 大規模なアーキテクチャ変更
- 根拠の薄い複雑な最適化

キャッシュは既存の無駄を隠し、整合性管理を複雑にするため、このPhaseでは導入しない。

## 完了条件

- 主要SQLのインデックス不足が解消されている
- 主要なN+1クエリが解消されている
- 高頻度経路の明白な重複処理が解消されている
- 次の改善にキャッシュ、データ保持方法の変更、サーバー分割などが必要になっている
- 採用した変更がGitへコミットされている
- ローカルから現在の構成を再デプロイできる

条件を満たしたらCodexはPhase 3への移行を提案し、人間が移行を決定する。
