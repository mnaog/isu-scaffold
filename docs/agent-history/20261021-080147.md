## [Claude] 2026-10-21T08:11:19.815+09:00

ベンチの中は見られないので、透かして見るとは、**ベンチを「アプリに要求を送り、応答に反応するクライアント」として外側から模型にすること**です。材料はサーバー側の観測と、参加者向けのベンチ出力だけです。この模型が合っていれば、「ここを速くすると、ベンチは次に何をするか」を測る前に予想できます。ninthで点が下がった回は、どれもこの予想が外れていました。

## 何を明らかにするか

| 問い | 例（ninth） | 外から見る方法 |
| --- | --- | --- |
| **主体と人数** | 利用者・椅子・オーナー。人数は評判と売上で増える | access logの`session`（nginxで記録済み）ごとの初出時刻を数え、時刻ごとの主体数の推移を見る |
| **次の要求のきっかけ** | 椅子は通知を受けてから座標を送る。オーナーは1〜2秒間隔 | 主体ごとに、前の応答の終わりから次の要求までの**間隔**を、遷移ごとに分布で見る。ほぼ0なら応答を待ってすぐ次へ進む型、一定なら時間で回す型、ばらつけば別のきっかけを待っている |
| **応答の内容による分岐** | 付近に椅子が無ければライドを作らず、nearby-chairsを繰り返す | 遷移に、直前の応答の内容（件数・状態・status）を付けて分ける。アプリ側で応答の要点を状態ログのattrsへ書く |
| **応答の速さへの反応** | 座標の応答を速くしたら、利用者の動きが変わって-18% | 1か所だけ遅らせる・速める実験で、遷移の回数と間隔の変化を見る |
| **ベンチが確かめること** | 評価の直後に支払いを確かめる（CODE=34）。椅子は評価が済むまで次に進まない（CODE=32） | 公式資料とFAILのmessageから、確かめる時機と前提を表にする。新しいFAILが出るたびに足す |
| **得点の内訳** | 売上が椅子の追加を呼び、評価がユーザーの増加を呼ぶ | access logやDBから模型scoreを作り、実scoreと比べる（`score-probe`） |

## そのために足りないもの

- **間隔と分岐が無い。** survey-runの遷移は「AのあとにB」の回数だけです。access logに`msec`・`reqtime`・`session`はもうあるので、遷移ごとの間隔の分布と、主体の数の推移をisuscope側で出すのが一番効きます。

## surveyの上乗せ（+4.7秒）の原因

isuscope-nodeを入れたのはrouteごとの集計（alp）で、surveyだけが使う次の2つはまだ古いやり方です。

1. **`nginx-log-raw` が生ログを圧縮せずに転送している。** commandは`cat`だけで、1 nodeあたり110MB（31.5万行）をsshで送っています。4.3〜4.6秒かかり、同じ順番待ちに並ぶalpはその後でしか始まりません。手元では5.7MBのzstで保存しているので、node上で圧縮してから送れば1秒未満になる見込みです。
2. **flamegraphのために`perf script`を2回走らせている。** `perf-flamegraph`は、`perf-series`とは別にもう一度`perf script`を走らせます（5〜7秒）。perfの処理は同じ順番待ち（`sequence = "perf"`）に並ぶので、そのぶん`perf-series`の開始が遅れます。`perf-series`の出力から作るか、surveyでも作らないかで、この待ちは消えます。

## 今のローカルの重さ（ninth、54 run）

`isuscope-data`は計8.1GBでした。内訳は次のとおりです。

| もの | 1 runあたり | 54 runの合計 | 中身 |
| --- | --- | --- | --- |
| **状態ログのcache**（`runs/<id>/logs/.state-cache/states.sqlite3`） | **約215MB** | **約6GB** | `states sql`・`timeline`用のSQLite。元の状態ログ（zstで5.3MB）の約40倍。run中に毎回作っている |
| 古い版の状態cache（`isuscope-data/cache/states/`） | — | 533MB | 3 run分 |
| 検索用DB（`isuscope.sqlite3`） | 約22MB | 1.2GB | 1 runあたり約8万行のmetric |
| 保存したログ（`logs/*.zst`） | 約7MB | 約0.4GB | |
| **追加：生のaccess log**（今回から毎run） | 約12MB（2 node分） | 約0.7GB | |

重くしているのはほぼ状態ログのcacheです。生のaccess logを毎回残しても、増えるのは全体の1割未満です。

ほかに次の2つも効いていそうです。

- **Time Machineの対象に入っている。** `tmutil isexcluded`で見ると、`~/project/isucon`はバックアップの対象（Included）です。毎run数百MBずつ書き換わるSQLiteを、1時間ごとにバックアップしている可能性があります。
- **Spotlightの除外もありません。** `.metadata_never_index`が無いので、生成物の索引作りも走っている可能性があります。

## 提案：ログの残し方

| もの | 残し方 | 理由 |
| --- | --- | --- |
| zstのログ（生のaccess log・状態ログ・ベンチ出力など） | **全runを手元に残す**。Gitには入れない（今どおり`logs/`はignore、重要なrunだけ`git add -f`） | ベンチの反応を、どのrunとでも後から比べられるようにする。1 runで約20MBなので、60 runでも約1.2GB |
| 状態ログのcache | **直近の数run（例：3）だけ残し、古いものは消す** | zstの状態ログから作り直せる使い捨てのcache。古いrunを`states sql`で読むときは、その場で作り直される（isuscopeの処理がその前提で書かれている。作り直しにかかる時間は未計測） |
| 検索用DB | そのまま | runから作り直せる。60 runで1.3GB程度 |
| `isuscope-data/`全体 | **Time MachineとSpotlightから外す** | 作り直せる生成物と、残すべきzstは、どちらもバックアップの頻度に合っていない。repoとして残すものはGitに入っている |

ローカルのCPUの面では、生ログは受け取ったzstをそのまま置くようにしたので、手元で圧縮し直す処理は今回なくしました。毎回増えるのは行動遷移の集計（約1.2秒）だけです。

## 実装について

状態ログのcacheを作る処理は、isuscopeのmainのcheckoutにある**未commitの変更**（`src/states/cache.rs`、10/20 19:12）の中にあります。これを書き換えるとその作業と衝突するので、古いcacheの掃除は**scaffold側**でやるのがよいと思います。ベンチを起動したときに走るhook（`scripts/bench-hook.py`）で、直近3 run以外の`.state-cache`と`isuscope-data/cache/`を消します。Time MachineとSpotlightからの除外は、準備の手順（`make`の準備用target）で一度だけ設定します。

広がりますが、増えるのは**材料と回数**です。今のままでは、それを使って探索する仕組みがまだ足りません。

## 増えるもの

- **どのrunでもベンチの反応を見られる。** ninthで「速くしたのに点が下がった」回は、どれも遷移も生ログも残っていませんでした。これからは毎回残るので、前のrunと並べて、ベンチ側の動きのどこが変わったかを後から調べられます。
- **回せる回数が少し増える。** 1周が4〜10秒縮むので、60 runの練習なら3〜6回分です。
- **ローカルの重さで止まりにくくなる。** 状態ログのcacheが溜まらないので、長い練習でもディスクとバックアップの負担が増えません。

## まだ足りないもの

1. **遷移を前のrunと比べる道具が無い。** `isuscope query --base`はHTTP・SQL・metricを比べられますが、遷移には対応していません。今は`brief`に、そのrunの遷移が単独で並ぶだけです。2つのrunの遷移を比べるには、手でSQLを書くことになります。
2. **比べるきっかけが手順に無い。** 「応答を変えた回は遷移を前と比べる」と書いたのは`docs/reference/isuscope.md`だけです。mainとimproveが毎回読む`/main`・`/improve`の手順や、見取り図の「ベンチの反応」の節には、まだ入れていません。
3. **遷移で見える範囲が狭い。** 遷移の間隔は前の要求の開始から次の要求の開始までなので、応答から次の要求までの考え時間は分かりません。応答の内容による分岐（空の応答なら繰り返す、など）や、時刻ごとの主体の数も出ません。生ログからは出せますが、今は都度scriptを書く必要があります。
4. **scoutに届く遷移は上位5件だけ。** scoutは`brief --limit 5`を読むので、前のrunとの違いは見ていません。

## 探索の幅を実際に広げるには

1を作るのが一番効きます。具体的には、`isuscope query --base`に遷移の比較を足し、遷移ごとに回数と間隔がどう変わったかを出します。これがあれば、2の手順は「点が予想と違う方向に動いたら、遷移を前のrunと比べる」という一行で済みます。scoutにも同じ比較を渡せます。3は、比較で気になる差が見えてから、生ログの集計を足すので十分だと思います。
