「記録CLI」は、**workerの作業状況を共通SQLiteへ登録する小さなコマンド**のことです。例えば、こんな入口です。

```bash
# workerが作業開始時に実行
python scripts/work.py start \
  --task "一覧取得のN+1を解消する" \
  --estimate-minutes 5

# 見込み変更や詰まりを記録
python scripts/work.py update --remaining-minutes 3 \
  --note "関連する呼び出し元も修正中"

# workerが開発完了を記録
python scripts/work.py complete \
  --validation "cargo test成功" \
  --notes "共有ベンチでの確認が必要"

# 統合後にoperatorが記録
python scripts/work.py integrated --task-id TASK_ID
```

名前や引数は例です。worktree・commit・時刻などは自動取得し、セッションIDなどは将来forkスキルから渡せるようにします。普段、人間が手入力するものではなく、workerやoperatorが実行し、その結果をボードに表示するための入口です。

調べました。**今のボードに足したいのは、人間が「気になる点を選んで、自分で確かめる」ための導線です。** 表示項目を増やすだけより、run比較とSQLite探索をつなぐ方が役に立ちます。

isuscopeには既に必要な土台があります。

- `query --base`：同じ条件で2つのrunを比較
- `series`：負荷区間を切り出し、時間経過に沿って調べる
- `sql`：保存済みSQLiteに読み取り専用SQLを実行
- `sql --schema`：テーブル定義を取得

確認したのは[README](/Users/nao/project/isucon/isuscope/README.md)、[SQL実装](/Users/nao/project/isucon/isuscope/src/sql.rs)、既存UIとscaffoldの実装です。今回、アプリの性能調査やベンチ実行はしていません。

**ボードへ追加するなら、この順がよいです。**

| 優先 | 追加するもの | 人間ができること |
|---|---|---|
| 高 | runを選択して比較 | グラフの点を選び、「この改善で何が変わったか」を調べる |
| 高 | HTTP・SQLの増減ランキング | 現在の上位だけでなく、悪化・改善した処理を見つける |
| 高 | 仮説・分析・変更の採否 | 何を試したrunか、何が分かり、何が保留かを確認する |
| 高 | 計測の欠落・比較条件 | スコア差がコード変更によるものか、観測条件も変わったのかを判断する |
| 中 | run内の時系列 | 負荷の後半だけ遅くなる、CPUが空いているのに応答が遅い、といった現象を掘る |
| 中 | main・deploy・計測時の版 | 「統合したが未デプロイ」「デプロイしたが未計測」を把握する |

仮説・分析・採否・計測欠落・比較条件は、isuscopeが既に持っています。今のボードでは省略している部分です。特に**スコアだけ上がっていても、計測条件が違うなら比較の意味が変わる**ので、ここは表に出したいです。

deploy情報もscaffoldに記録があります。ただし、ボードには「最後に記録したdeploy」として表示し、現在のremote実体を確認済みとは扱わないのが正確です。

**SQLite探索は、画面内に設ける価値があります。**

こんな構成を考えています。

```text
概要     比較     探索

探索対象：isuscope計測DB / scaffold運用DB
対象run：xxxxxxxx    比較元：yyyyyyyy

[テーブル・カラム一覧]  [SQLエディタ]
                       [実行] [キャンセル]

[結果の表 / グラフ]
[SQL・結果・対象runをコピー]
```

最初は次の機能があれば十分です。

- **SQLを自由に書ける。** isuscope側は既存の`isuscope sql`を利用する。
- **定型クエリから始められる。** 「存在するmetric一覧」「エラー内訳」「node別負荷」「失敗したcollector」など。
- **結果を並べ替え・絞り込みできる。** 時刻と数値の結果は折れ線にもできる。
- **クエリを保存・再実行できる。** 名前付き保存と直近の実行履歴はローカルへ残す。
- **operatorへ根拠ごと渡せる。** run ID、SQL、結果をまとめてコピーする。自動注入はしない。

探索対象はまず、**保存済みの計測DBとscaffoldの運用DB**がよいです。アプリの稼働中DBを直接触る機能とは分けます。isuscopeのSQLiteは再構築される索引なので、分析や採否をSQLで書き換える入口にはしません。

実装上の注意も一つあります。既存の`isuscope sql --limit`は**返す行数の上限**で、重い集計の実行時間までは制限しません。画面から使う際には実行時間・結果サイズの上限とキャンセルを付けます。

人間の操作としては、例えばこうなります。

> スコアが伸びなかったrunを選ぶ  
> → SQL時間は減ったが、HTTP処理数が増えていないことに気づく  
> → ホスト負荷や接続の時系列を見る  
> → 気になる部分をSQLで絞る  
> → 根拠を添えてoperatorへ次の調査を渡す

そのため、次の実装は **「グラフからrun選択 → 比較画面 → SQL探索」** を一続きにするのを推します。探索中は選択runを固定し、新しいrunが来ても勝手に切り替えないようにします。トップ画面は今の簡潔さを保てます。
