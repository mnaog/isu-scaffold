最初のSSHでサーバーのPython版を取得し、事前に動作確認したAnsible環境を選ぶ。 対応するコントローラ側の依存も準備しておき、当日に互換性を調べながらpipの依存を解き直す時間を減らす。

これは正常時の数秒を削る変更ではなく、特定の配布環境で数分以上の調査・復旧へ入ることを防ぐ変更。既に遭遇した問題なので、優先度は高い。

3. 初回ベンチまでなら有力：完全importで target/ を回収し直している
これは今回、具体的な無駄として確認できた。

先行回収の quick-import-code.sh は、Rustの target/、node_modules/、.git/ を除外する。一方、後の完全importは、対象ディレクトリ全体について以下を行う。

配布先の各サーバーで、全ファイルの内容を読み、digestを計算。
ローカルでも同じ計算。
一致しなければ、除外なしのtarでディレクトリ全体を転送。
転送後、再びdigestを計算して検証。
先行回収で除いた target/ を、完全importでは再び扱っている。 先行回収の除外・完全importの実装

実際の練習にも、その影響が出る条件があった。

練習    target/ 生成物を含むRustディレクトリ
ISUCON12 fifth    1,048 MiB
ISUCON11本選    889 MiB
ISUCON14    721 MiB
12 fifthの記録には、明示的に「targetを含めてdigest比較・回収」「容量と回収待ち時間を許容」とある。12 fifth・11本選・14

改善案
「ローカルで管理する初期ソース」と「配布環境のビルド生成物」の扱いを、同期設定で明確にする。

Rustのビルドキャッシュを除外するなら、転送とdigest計算の両方に、同じ除外ルールを適用する。tarだけ除外すると検証に失敗する。

また、元の実行ファイルや実行時データが必要なら、それは明示的に保持する。target/ という名前だから一律に不要と決める実装にはしない。

これによって、不要な内容の読み出し・照合・転送に加え、ソースが同じなのにビルド生成物の差だけで「サーバー間不一致」となる問題も減らせる。

ただし、これは主に kickoff-apply に効く改善。make kickoff 単体の実行時間は直接縮まらない。95〜108秒のうち何秒を占めたかは、現在の記録では分離できていない。

4. make kickoff 本体なら、Ansibleの調査処理をまとめたい
現行の inspect.yml は、情報収集のための細かい処理が多い。

現状    変更案
17種類のコマンドの版確認を、Ansibleのloopで個別実行    1回のリモートスクリプトでまとめて収集
/home /opt /srv のアプリ候補検索を、候補取得・所有者取得で2回実行    1回の検索結果から両方を生成
全サービスについて1つずつ systemctl show    まとめて問い合わせる
bootstrap後、別のAnsible実行でOS・CPU等のfactsを再収集    同じ実行内で静的な情報を再利用
draft reviewの主要情報は並列取得するが、後段の nginx -T はサーバーごとに逐次取得    並列取得する処理へ含める
出典：inspect.yml・review-draft.py

特に17種類の確認は、必要な情報を保ったまま、Ansibleモジュールを起動する回数を減らせる。systemctl の集約も同様。ただしこちらはSSH往復ではなく、サーバー内のプロセス起動・問い合わせの削減になる。

factsの再利用には少し設計が必要。Ansibleの標準メモリキャッシュは、同じplaybook実行の間だけ有効なので、別プロセスのまま gather_facts: false にするだけでは成立しない。bootstrapとinspectionを同じ実行にまとめ、OS・CPUなどを再利用しつつ、準備後に変わるサービス・ログ・ツールの状態は再取得するのが自然。

効果の見込み
過去の実測では、inspect-environment.sh の再実行が 24.2秒だった。

そのため、この試走に限れば、調査処理を全部なくしても短縮上限は24.2秒。実際には情報収集を残すので、それより小さい。ここだけで初動が数分縮むとは言えないが、確実に無駄を削る対象としてよい。

同じ流れにある、小さな重複も削れる
初回 kickoff は最初に discover し、回収元1台のSSHを確立する。その後の bootstrap.sh が、再び discover と全台SSH確認を行う。

同じkickoff実行内で取得した接続情報と、成功したSSH接続を再利用する余地がある。 最初の発見後、他のサーバーのSSH確立を、回収元からのコード転送に重ねる案もある。kickoff.sh・bootstrap.sh

ここは同一実行内の再利用に限定したい。次の試走で古い接続先を使ってしまうような永続キャッシュは必要ない。

5. 初回のダウンロード・ビルダー準備を減らす
計測ツールは、既存機能で事前準備できる
今のbootstrapは、各サーバーでalp・slpをダウンロードし、FlameGraphを取得する。一方で、ローカルに準備したツールを配る observability_local_tools は既に実装済み。tools.yml

これを使えば、競技開始後の外部ダウンロードを、準備済みファイルの配布に置き換えられる。

注意点は、observability_local_tools を設定しただけでは、元のダウンロード処理も残ること。必要なファイルを揃え、observability_download_tools=false と組み合わせる必要がある。

なお、Ansible自体の事前インストールは、すでにPhase 0の手順に入っている。そこを実施済みなら、「Ansibleを事前に入れる」は新しい改善にはならない。Phase 0

6. ビルド設定待ちは「通知と進行の設計」を改善する
前の回答の論点も、実装上は残っている。

現在、BUILD NEEDS CONFIGURATION はビルド用ログへ出力される。kickoff の標準出力でビルド状態を確認するのは、bootstrap・inspection・draft reviewが終わった最後。

同じエージェントが make kickoff の終了を待っていると、設定の確定が遅れ、並行ビルドの効果を失う可能性がある。 phase1-build.py

ただ、実走では設定を36〜48秒で渡せていた。したがって、毎回ここで数分失っている、という見立ては撤回する。

改善するなら、次の状態を、実行中のエージェントがすぐ認識できるようにする。

コード回収完了
ビルド設定が必要
ビルド開始・終了
draft確認可能
初動処理の失敗
これは設定待ちだけでなく、失敗の発見にも効く。fourthでは、時間記録から算出した kickoff の終了から、修正後のinspection再開まで約3分52秒あった。ただし、その間もビルドなどは進んでいるため、全時間がそのまま短縮できるわけではない。fourthの実行履歴

7. 大きく並列化する前に気をつけたい点
make -j やAnsibleの並列数を増やすだけでは、今回の主な待ちは解消しない。

主処理は kickoff.sh 内で順番に呼ばれており、Ansibleも既に forks=10、SSH pipeliningが有効。先行ビルド、SSH接続、完全importのサーバー間並列化も入っている。Ansible設定・初動仕様

一方、構造的な待ちはある。今のbootstrapは、アプリ・ベンチサーバーの全台で初期構築完了を待ってから、アプリ側の計測準備へ進む。ベンチサーバーだけ構築が遅い場合、準備済みアプリサーバーの作業まで遅れる。 bootstrap.yml

将来的には「各サーバーの構築完了後、そのサーバーの準備を進め、最後に全体成功を確認する」方式が候補になる。

ただし、単純な strategy: free 追加では不十分。freeで先行できるのは現在のplayの終わりまでで、現行の any_errors_fatal とも挙動が変わる。実測で全台待ちが支配的だと分かってから取り組む、比較的大きな変更として扱いたい。

僕なら、この順で手を入れる

これらと一緒に、kickoff の内部工程別の時間を記録する修正は入れたい。 現在の operation-timing.tsv は、外側の kickoff がロックを取ると、内部のbootstrapなどが個別の時間記録を残さない。ビルドの表示時間もイメージ準備を含まないため、今のログだけでは原因を分けきれない。ロックと時間記録の実装

評価する時刻は、コードを読める時刻・draftが揃う時刻・初期ビルド完了時刻・初回ベンチを開始できる時刻の4つでよい。

現時点では、「設定待ちを削れば何分短くなる」という根拠はない。まず既知の停止原因と大容量の不要回収を取り除き、kickoff 本体の細かい調査処理をまとめる。この順が、今あるコードと実走記録から最も効果を期待できる。
