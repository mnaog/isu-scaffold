**毎回surveyの内容を全部追加すると重くなります。ただし、ユーザー遷移の集計だけなら、毎回取る価値はあります。** 勝つことが目的なら、「得られる情報で次の改善判断が変わるか」と「改善サイクルが何秒延びるか」で決めたいです。

重さは分けて考える必要があります。

| 追加するもの | 主に増える負担 | 判断 |
|---|---|---|
| Cookie由来の識別子をログへ記録 | ログ量・書き込み | こちらは既に記録する設定なので、毎回集計にしても新規負担ではない |
| 遷移の集計 | ベンチ後のCPU・メモリ・処理時間 | 軽量化して毎回取る候補 |
| 生access/slow logの全量回収 | 転送・保存・後処理時間 | 通常runでは省く方針を維持したい |
| HTTP本文の全件capture | ベンチ中の中継・処理負荷 | 必要な調査に限定 |
| Flame Graph生成 | ベンチ後の追加処理 | 関数別集計で足りないときに生成 |

**勝つためのおすすめは「通常runの計測条件を固定し、遷移は軽い集計を毎回残す」です。** 初回だけでは、性能改善によってユーザーの行動が先へ進み、新しいボトルネックが現れたときに追いにくいからです。

ただ、優先順位はこう考えます。

1. **既に毎回取れているHTTP・SQL・CPU・時系列を使い切る。**  
   まずここで次の変更を決められるボードにする。新しい計測負荷を増やさず効果が出ます。

2. **遷移の時刻精度を直し、毎回の軽量集計を追加する。**  
   遷移回数、session数、時間差、観測率、並行実行の割合を残す。今の秒精度のまま回数だけ増やしても、判断材料の質が足りません。

3. **生ログ全量・本文captureなどは、具体的な疑問があるときだけ使う。**  
   「この情報がないから次の施策を選べない」という場面に絞ります。

実際の追加秒数はまだ測っていません。**導入時に一度、ベンチ中の負荷と終了後の待ち時間を確認し、通常runへの常設を判断する**のがよいです。集計を別処理にする場合も、次のベンチにCPU負荷が重ならないようにします。

僕なら、**survey全部の毎回実行は見送り、正確なユーザー遷移の軽量集計は毎回取れるようにします。** ボードの項目数より、限られた時間で「根拠のある変更→評価」を何回回せるかを優先します。

## [Codex] 2026-10-04T01:26:04.701+09:00

**その形はよいと思います。初回surveyで遷移図を作り、各runの計測値を重ねる**と、「どこに時間を使い、その先の処理にどれだけ進めているか」を見やすくできます。

図は次のように分けるのがおすすめです。

| 表示 | 内容 | 更新するタイミング |
|---|---|---|
| ノード | 正規化したAPI | 初回survey |
| 矢印 | session内で観測したAPI間の遷移 | 初回survey |
| ノード内の数値 | 選択runの要求回数、平均／p95、エラー数 | run切り替え時 |
| ノードの色 | 選択runの合計処理時間 | run切り替え時 |
| 矢印の数値 | **初回survey時点の**遷移回数 | 固定・必要時だけ表示 |

例えば、ノードにこう出します。

> `POST /example`  
> 12,000回 · 平均8ms · p95 24ms  
> 合計96秒 · エラー0件

**回数だけでなく、合計時間と1回あたりの時間を一緒に見るのが大事です。** 回数が多くて負荷が大きいAPIと、少数でも遅くて後続処理を待たせるAPIを区別できます。ただし、合計時間は並行処理も足した値なので、そのままベンチ全体の待ち時間ではありません。

実装は次の形が合います。

1. 初回surveyの遷移から、Mermaid図を自動生成する。
2. 人間が確認し、並行呼び出しや別シナリオを整理する。
3. ボードに固定のシナリオ図として表示する。
4. 選択runのHTTP計測でノードの数値・色を更新する。
5. ノードから既存のHTTP詳細を開けるようにする。

現状の遷移集計は秒精度の時刻を使うため、**図を自動生成する前に、開始時刻と並行実行の扱いを直したい**です。観測順をそのまま確定したシナリオとして描くと、誤った矢印が判断を邪魔します。

まずは **「初回の遷移図＋選択runのAPI別計測」** がよいです。遷移を毎回取り直さず、図を改善判断に使えます。
