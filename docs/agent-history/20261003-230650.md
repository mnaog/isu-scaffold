  `scripts/check-deployment.py`がworkerの受け渡し記録に依存しています。受け渡しDBへの依存は消しますが、必要なファイル・migrationが配布設定に含まれるかの検査は、役割に依存しない形で残します。

逆に、以下は残します。

- コードの先行回収、初期状態のcommit、非同期build、環境準備の自動化
- `.local/operation.lock`による変更操作の排他
- ローカルを正とする管理、deploy・rollback・配布検査
- baselineの保護とisuscopeの計測・採否記録
- worktreeごとのローカルDB・port・network分離

**ベストなのは、ベンチ後に「何が変わったか」「どこを疑うか」「次に何を確かめるか」を人間が素早く決められるボードだと思います。** 詳細な情報は十分に持たせ、その入口を整理したいです。

今のこちらは計測項目が増えましたが、まだ「計測を順に並べた画面」に近い。みねおさんのtemplateからは詳細の切り替えとシナリオ別の内訳を、pproteinからは計測結果をひとまとまりとして掘れる操作を取り入れるのがよさそうです。

pproteinにもWeb UIがあります。確認した実装では、同じ計測グループ内で種類・対象別の結果を切り替え、HTTP／SQLの表やpprofのflamegraphを開けます。参考になるのは、**気になった計測を、そのまま詳しく調べられる近さ**です。[計測切り替え](https://github.com/kaz/pprotein/blob/fd0b0b1da93994dc4abb986222b92606c4fe9b2b/view/src/components/GroupEntry.vue)、[プロファイル表示](https://github.com/kaz/pprotein/blob/fd0b0b1da93994dc4abb986222b92606c4fe9b2b/view/src/components/PProfEntry.vue)

僕なら、次の構成にします。以下は実装済み機能の説明ではなく、設計案です。

| 画面 | 人間が答えたいこと | 主な表示 |
|---|---|---|
| **概要** | 今回は良くなったか。次はどこを見るか | スコア差、PASS／FAIL、初期化、主要な変化、資源の偏り、計測欠落 |
| **時間軸** | いつ、何と一緒に悪くなったか | 成功件数・エラー・遅延・CPU・I/O・DB待ちを同期表示 |
| **HTTP** | どの処理が重いか。回数か、1回の遅さか | 回数・平均・p95・合計時間・エラー・比較差分、対象別内訳 |
| **SQL** | DBの何に時間を使っているか | digest別の回数・時間・ロック・走査行数、SQL詳細 |
| **シナリオ** | どんな行動が多く、どこで滞るか | 全体／シナリオ群別の遷移、利用人数、所要時間、API負荷 |
| **構成・プロファイル** | どのサーバー・サービス・関数が制約か | 計測時の構成、資源負荷、関数一覧、取得できればflamegraph |
| **実験履歴** | 何を試し、何が効いて、何が未解決か | run・commit・仮説・観測・採否・比較元 |

全画面で、**対象run・比較元・サーバー・計測区間**を共通にします。タブを移っても選択を維持し、深掘りして戻っても並び順や選択が消えないようにする。タブは情報を十分に載せるために使い、異常の存在は概要にも出します。

**最初の概要画面が、いちばん重要です。**

大きなスコアとグラフだけでは、気づきは限定的です。例えば次のような「観測の組み合わせ」を、根拠へのリンク付きで出したいです。

- **合計時間は増えたが、平均時間は短縮した**  
  処理件数が増えた結果かもしれない。単純な悪化として赤くしない。
- **全体CPUには余裕があるが、1コアだけ張り付いている**  
  単一スレッドや直列処理を調べる入口になる。
- **エラー増加と同時に、成功件数とCPUが落ちている**  
  負荷が軽くなったことを性能改善と誤認しない。
- **変更対象のSQLは改善したが、スコアは伸びていない**  
  別の制約へ移った可能性を調べる。

これはAIに断定的な診断を書かせるより、まず保存済みの数値から作れる観測として表示します。scoutの解釈は、その隣に根拠付きで置くのがよいです。

**ランキングは、一つに絞らない方がいいです。**

HTTPやSQLを合計時間順にするだけでは、「頻度は低いが、成功に必須の遅い処理」を見落とします。少なくとも次の切り替えが必要です。

| 見方 | 発見しやすいこと |
|---|---|
| 合計時間が大きい | 全体への負担が大きい処理 |
| 1回が遅い・p95が悪い | タイムアウトや待ち時間につながる処理 |
| 回数が多い | N+1、重複、ポーリング |
| 比較元から悪化した | 直近変更の副作用 |
| エラーが増えた | スコアや正しさを損なう処理 |

合計時間の割合を「ここを直せばスコアが何％上がる」とは扱いません。並行実行や待ち時間を含むため、改善候補を探す根拠として使います。

**シナリオ画面は、こちらで特に伸ばす価値があります。**

現在の「初回surveyの図に、選択runのAPI計測を重ねる」は入口として有効です。ただ、全部を一枚にすると矢印が増え、行動の違いが見えにくくなります。

みねおさんのtemplateにある、**全体からシナリオ群を選び、その群の人数・要求数・時間・開始／終了APIを見る構成**を取り入れたいです。[シナリオ群の表示実装](https://github.com/EkeMinusYou/isucon-template/blob/f3f61717f24ab28ec109df1a99aa85b54c22149b/tools/dashboard/web/src/components/UserTransitions.tsx)

ただし、Cookie等から観測した行動群と、公式の採点シナリオは別です。また、初回surveyの人数や遷移回数を、選択runの値に見せてはいけません。**構造の取得runと、重ねている性能値のrunは常に明示**します。APIとSQLの対応も、時間が似ているだけで自動的に結び付けず、コード読解や計測で確認できた関係だけを載せます。

実装の優先順位はこう考えます。

1. **既存データを使った概要・差分・詳細への導線**  
   最も早く、改善判断の時間を短くできる。
2. **共通フィルターと同期した時間軸**  
   別々のグラフで起きている現象を結び付けやすくする。時間範囲での再集計には、対応するデータが必要。
3. **シナリオ群別の集計と切り替え**  
   表示変更だけでなく、遷移の集計処理を追加する。
4. **不足している計測の追加**  
   cache HIT/MISSや詳細プロファイルなど。取得負荷と用途を確認して加える。

評価基準も、タブ数やグラフ数ではなく、**ベンチ終了から根拠のある次の仮説を選ぶまでの時間、比較条件の取り違え、見落とした退行の数**にしたいです。人間が「この数字が気になる」と感じ、その根拠まで迷わず辿れることを、ボードの中心に置くのがよいと思います。

## [Codex] 2026-10-04T10:42:16.038+09:00

「次に確かめること」は、**固定条件に当てはまった数値を、説明文付きで表示する仕組み**です。AIが毎回分析しているわけではありません。

例えば、次を検出しています。

- 平均時間が比較元より20%以上増加
- HTTPエラー数が増加
- 回数・合計時間が増え、平均時間は短縮
- 平均CPUが60%未満で、最繁忙コアのpeakが90%以上
- I/O waitが10%以上

ただ、**閾値や取り上げる観点はこちらが決めたものなので、解釈と優先順位を持ち込んでいます。** 「気づきを与える」を、こちらが見るべき場所を勧めることに寄せすぎました。

このボードでは、**数値・差分・分布・時系列を見比べやすくし、人間が解釈する**方が合っています。「次に確かめること」は外し、概要にはスコア、PASS／FAIL、初期化時間、計測欠落と、HTTP／SQLの比較表への入口を置くのがよいと思います。

回数・平均・合計時間は並べて表示すれば十分で、「悪化と判断しない」といった説明を毎回出す必要はありません。欠測や比較区間の違いなど、**数字を正しく読むための注記**は残します。

## [Codex] 2026-10-04T11:27:43.393+09:00

伝わっています。求めているのは、**人間が計測結果を眺めながら違和感や関係に気づき、次の改善を考えられる、ISUCONで勝つための観測画面**だと理解しています。

ここまでの指摘には一貫性があります。

- **情報は豊富でいい。** 減らしたいのは、情報へ到達するためのクリックや操作。
- **スクロールで見渡したい。** タブで情報を分断せず、別の計測との関係を目に入れたい。
- **判断を先回りしすぎない。** 自動生成の「次に確かめること」より、判断材料を見せてほしい。
- **補助操作は控えめでいい。** 比較条件や表示設定は必要だけれど、常時読むデータと同じ存在感はいらない。
- **見ただけで意味が分かってほしい。** 抽象的な名前、実装用語、停止表示、取得コマンドなどで考える負担を増やしたくない。
- **図には、表とは違う役割がほしい。** 数値を箱へ詰めるだけでなく、流れ・分岐・集中が視覚的に分かるもの。

僕は途中まで「機能を追加すれば便利になる」と考えすぎていました。並べ替えボタン、タブ、説明、提案を足した結果、情報を見る前に操作や文章を読ませる画面になっていました。

みねおさんのものから取り入れるべきなのも、機能やタブの数より、**情報の関係と強弱を視覚的に伝えるところ**です。今回確認した図では、流れを配置と曲線で示し、APIと計測値を結び付けています。こちらでは、その良さをスクロール中心の構成に合わせるのがよいと思います。

今の画面は、操作の整理と見出しの具体化が進みました。ただ、まだ「計測項目を順に並べた画面」の要素が強いです。次は以下を改善したいです。

| 改善するところ | 狙い |
|---|---|
| **実データのAPI図** | 今回は表示例が特に改善した一方、実データ側はMermaidの箱が中心。実際のデータでも、流れと負荷の集中を読みやすくする |
| **HTTP・SQLの表の視覚的な強弱** | API・SQL、合計時間、差分を主役にして、補助値を控えめにする。行を追うだけで目立つ箇所を見つけられるようにする |
| **計測同士の対応** | HTTPの増加とCPU・SQLの変化など、同じ時刻の現象を照合しやすくする。因果関係は勝手に断定しない |
| **情報密度の配分** | 空欄や説明に使う面積を抑え、実データに面積を使う。未取得とゼロの区別は保つ |
| **比較の一貫性** | 何と何の比較か、どの区間か、差分の向きがどこでも同じ読み方になるようにする |

優先するなら、**実データが多い状態での図と表の読みやすさ**です。今のプレビューはHTTPが1行、SQLが空なので、混雑したときの見やすさまでは確認できていません。APIの分岐・循環、長いSQL、複数サーバー、改善と悪化が混在する表示用データで詰めるのが、次の一歩として効果的です。

目指す基準は「機能が多いか」ではなく、**開いたときに、変化した場所・時間がかかる場所・気になる関係が自然に目に入るか**です。
