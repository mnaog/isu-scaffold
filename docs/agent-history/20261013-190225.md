最初のSSHでサーバーのPython版を取得し、事前に動作確認したAnsible環境を選ぶ。 対応するコントローラ側の依存も準備しておき、当日に互換性を調べながらpipの依存を解き直す時間を減らす。

3. 初回ベンチまでなら有力：完全importで target/ を回収し直している
これは今回、具体的な無駄として確認できた。

先行回収の quick-import-code.sh は、Rustの target/、node_modules/、.git/ を除外する。一方、後の完全importは、対象ディレクトリ全体について以下を行う。

配布先の各サーバーで、全ファイルの内容を読み、digestを計算。
ローカルでも同じ計算。
一致しなければ、除外なしのtarでディレクトリ全体を転送。

先行回収で除いた target/ を、完全importでは再び扱っている。 先行回収の除外・完全importの実装

改善案
「ローカルで管理する初期ソース」と「配布環境のビルド生成物」の扱いを、同期設定で明確にする。

Rustのビルドキャッシュを除外するなら、転送とdigest計算の両方に、同じ除外ルールを適用する。tarだけ除外すると検証に失敗する。

また、元の実行ファイルや実行時データが必要なら、それは明示的に保持する。target/ という名前だから一律に不要と決める実装にはしない。

これによって、不要な内容の読み出し・照合・転送に加え、ソースが同じなのにビルド生成物の差だけで「サーバー間不一致」となる問題も減らせる。

FlameGraphは、CPUがどの関数で時間を使っているかを1枚の図で見せる道具です。Brendan Greggが作ったPerlのscript群（`stackcollapse-perf.pl`、`flamegraph.pl`）です。

## 図の見方

- **横幅**：その関数（と、そこから呼んだ関数）にCPUを使った時間の割合です。幅が広いほど重く、横の並び順には意味がありません。
- **縦**：呼び出しの階層です。下が呼び出し元、上が呼び出し先です。
- 上の端が平らで幅の広い箱が、実際にCPUを使っている場所です。

たとえば`main → handler → serde_json::to_string`が横の4割を占めていれば、JSONの生成がCPUの4割を使っている、と一目で分かります。

## isuscopeでの使い方

1. ベンチの間、`perf record`がCPUのsamplingで呼び出しの積み重なりを記録します。
2. `stackcollapse-perf.pl`が、その記録を1行1つの積み重なりにまとめます。
3. `flamegraph.pl`が、それをSVGの図にします。

isuscopeのREADMEによると、flame graphは既定で`survey-run`のときだけ作ります。perfの記録を読み直す処理がもう1回増えるためです。普段の`run`では、関数ごとのCPUの割合（`perf-series`）だけを数字で残しています。

前の話でいうと、各サーバーで`git clone`しているのはこのscript群です。CPUの種類に関係ないPerlのscriptなので、事前に1回落としておけば全台に配れます。

では、1〜4を実装してよければ進めます。

flame graphを作っているのは、isuscopeの`perf-flamegraph`というcollectorだけです。それも、既定では初回の`survey-run`のときしか動きません。

## どこで作られるか

isuscopeのひな形の設定（`templates/config.toml`の477行目）に、`perf-flamegraph`があります。

- **動くとき**：`modes = ["survey-run"]`なので、初回調査の`survey-run`だけです。普段の`isuscope run`では動きません。
- **動く場所**：app roleのnodeで、ベンチの後に動きます。ベンチ中に`perf record`が取った`perf.data`を、`perf script` → `stackcollapse-perf.pl` → `flamegraph.pl`の順で処理してSVGにします。
- **なかったとき**：toolがないと`exit 75`（取れなかった扱い）で飛ばし、runは止まりません。

## 作った図の行き先

- **保存先**：runの`logs/perf-flamegraph-<node>-after-stdout.zst`です。practice-14の初回runにも、app1〜3の分が残っていました。
- **表示**：`isuscope report`のHTMLが`profiles`の欄にSVGへのリンクを出します（`src/report.rs`の590行目）。人が見るための図です。
- **AIの判断材料**：使っていません。`brief`が出すのは、profileが取れなかったという件数だけです。CPUの数値は、毎回動く`perf-series`が関数ごとの割合で出しています（run全体と5秒ごと）。AIはそちらを読みます。

## scaffold側の扱い

- **導入**：bootstrapのAnsible（`ansible/roles/observability/tasks/tools.yml`の38行目）が、各nodeへ`git clone`して入れています。
- **存在の確認**：
  - inspectionの`ansible/playbooks/inspect.yml`
  - draft生成の`scripts/configure-draft.py`
  - `isuscope doctor`

つまり、なくても毎回のベンチや判断には影響しません。困るのは、初回の`survey-run`で人が見る図が1枚欠けることだけです。1の事前準備の中では、FlameGraphは「入れば便利」くらいの重さです。失敗を防ぐ意味が大きいのは、毎回のベンチで使うalpとslpのほうです。
