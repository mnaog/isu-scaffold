**1. `wal`（`after: full-memory`）：最も効果が大きい**
- WAL化は試した5回すべてで採用され、どれも大きく伸びました。今の練習では、全メモリ化から1〜2時間後にimproveか人間が書いています。
- WALへの置き換えは全メモリ化のstoreを前提にした機械的な書き換えで、出力も決まっています。full-memoryが終わったら自動で始まるlaneにできます。
- laneは書き込みを置き換えるだけで、初期データからの再構築、initialize、再起動後の再生、`docs/cache-design.md`の更新を範囲に含めます。
- 「書き込みが律速と測れてからDBを外す」規則は変えません。laneはbranchを用意するだけで、いつmergeするかはmainが決めます。

**2. `runtime`（kickoffで起動、15〜20分）**
- 対象は、log levelのwarn化とTraceLayerの撤去、mimalloc、TCP_NODELAY、sqlxの`ssl_mode Disabled`とpool size、短い区間を守るlockのtokio Mutexからstd Mutexへの変更です。1件1commitにします。
- どれも小さく、ほぼ`main.rs`と`Cargo.toml`だけで済みます。obvious-fixesに足すこともできますが、あちらは90分のlaneでSQLとlogicが対象なので、分けた方が早く届きます。

**3. `static-edge`（config/nginxだけを変える）**
- 対象は、appが返している静的ファイルをnginxから配ること、hash付きのassetとHTML・SPAの入口へのCache-Control、`open_file_cache`です。gzip_staticは結果が割れているので別のcommitにします。
- どのpathが静的で、SPAのfallbackがどうなっているかは配布物を読まないと決まらないので、scriptよりlaneが合います。
- tareと同じsiteファイルを触るため、tareを入れた後に取り込む順番にします。

## laneにせず、scriptやscaffoldで直すべきもの

- **既定のaccess.logの停止**は判断が要らず、8回同じ修正をしています。`tare.py`（またはbootstrap）で、LTSVがあるときは既定のaccess_logを外すようにすれば、毎回の修正が要らなくなります。
- **MySQLの耐久性設定**も判断の余地がない定型の設定なので、tareと同じ形の`make durability`のような1commitを作るscriptが合います。耐久性はtareから意図的に外してあるので、deployする時機はmainがCOMMIT・iowaitを見て決めます。

## lane化しないもの

- DBを別nodeへ分けること、TLS終端の分散、HTTP/2、TLS session cache：観測を見て判断するもので、結果が割れたものもあります。
- matching、polling・SSE、決済の再送、nearbyの猶予：ISUCON14に固有の改善です。
- deadlock時のやり直し：WAL化すると要らなくなります。
- 終了前に計測を外すこと：`finish.md`の手順で足ります。

既存のlane（indexes・n-plus-one・obvious-fixes・full-memory）は、14の7〜9回目で出力がすべて採用されており、定型化はうまくいっています。
