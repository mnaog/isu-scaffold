**1. 今のコードで成立する部分と、壊れる部分**

**①［優先度高］採否反映より先に次のmergeが走る。依存投稿を取り込んだまま測定対象から外せる**

`isuscope analyze … && git merge …`では、投稿への採否反映は`analyze`直後ではなく、**呼び出し全体が戻った後のPostToolUse**です。ベンチを別呼び出しにする説明は正しいものの、前半にも順序問題が残ります。[bench.rs:26](/Users/nao/project/isucon/isu-scaffold/tools/isu-hook/src/bench.rs:26)

具体的には、Aを測定中、Aに依存するBがキューにある場合です。

1. Aの不採用をisuscopeへ記録する。
2. Aをrevertし、通知に載っていたBをmergeする。
3. PostToolUseがAの不採用を投稿へ写す。
4. `drop_dependents`がBを`deferred`にする。
5. 次の起動では、Bは`measuring`にならない。しかしBのコードはHEADに入っている。

`drop_dependents`は`merged`も対象にし、コードをrevertしません。`start_measuring`は`merged`だけを測定中にします。[proposal.py:630](/Users/nao/project/isucon/isu-scaffold/scripts/proposal.py:630)、[proposal.py:533](/Users/nao/project/isucon/isu-scaffold/scripts/proposal.py:533)

**修正案：採否を投稿へ同期し、依存投稿の除外が終わってから、次候補の有効性を再確認してmergeする。** 呼び出しを増やしたくなければ、この順序を明示した専用コマンドにします。単純な`&&`連結では不十分です。

**②［既存不具合・優先度高］投稿へ写すrun IDが、測定runではなく比較元になる**

**⑤ 詳しい分析を次のベンチ中に通知する経路は成立する。ただし「毎回すべて届く」わけではない**

**2. Monitorへ渡す情報は、案のままでは採否に足りない**

最初の`tail`往復をなくす狙いには賛成です。ただし、挙がっている項目には「期待する観測値」はあっても、**実測値、計測の欠落、比較条件の違い**がありません。

score差だけで採否を決めると、期待した改善が起きたか分からないまま、振れに反応することになります。自由文の`expect`から機械的に必要な観測を取り出すことも、現状では保証できません。

通知には最低限、次を載せたいです。

| 情報 | 必要な区別 |
|---|---|
| 今回のrun | ID、対象commit、結果、score |
| 比較元 | ID、差、比較条件の違い・不明 |
| 振れ幅 | 対象構成、件数、範囲、今回や比較元との対応 |
| 測った投稿 | change ID、commit、期待と取得できた実測値 |
| 不足・異常 | 計測欠落、主要な警告、追加確認が必要な点 |
| 次候補 | 候補commit、依存関係、どの構成でprebuildしたか |

二つ注意があります。

- **今のbriefの振れ幅は、今回の構成の振れ幅とは限りません。** `latest_spread`は「2回以上測った組のうち最後に測られた組」を返します。別の構成でも返るので、対象を省略して「振れ幅±…」と載せるのは危険です。[brief.rs:507](/Users/nao/project/isucon/isuscope/src/brief.rs:507)
- **prebuild成功は候補branch全般の成功ではありません。** 現状は採用継続／測定投稿を全てrevertした構成と、候補1件の組み合わせを最大6通り作ります。部分採用や複数候補の組み合わせは未検証になり得ます。結果の`head`・`variant`・`tree`との対応が必要です。[prebuild.py:76](/Users/nao/project/isucon/isu-scaffold/scripts/prebuild.py:76)、[prebuild.py:180](/Users/nao/project/isucon/isu-scaffold/scripts/prebuild.py:180)

「1行」は配送形式としては問題ありませんが、情報量の目標にはしない方がよいです。長い1行へbrief相当を詰めれば、減るのはツール往復であって読む時間ではありません。既存の`brief --json`を利用し、**少数の判断材料と、不足している事実を明示する要約**がよいと思います。

Monitorの扱いにも小さな落とし穴があります。

- `source=main`で出すと、main自身には届きません。[progress.py:73](/Users/nao/project/isucon/isu-scaffold/scripts/progress.py:73)
- `emit`は書き込み失敗を握りつぶします。通知を唯一の記録にはできません。[progress.py:37](/Users/nao/project/isucon/isu-scaffold/scripts/progress.py:37)
- `follow`は起動時にだけルールを読み、通常は既存行を読み飛ばします。途中での設定変更やMonitor再起動には回復手順が必要です。[progress.py:81](/Users/nao/project/isucon/isu-scaffold/scripts/progress.py:81)

バックグラウンド完了通知との二重配送は、run IDをキーに「同じ完了を再処理しない」と決めれば許容できます。通知を一つにすることより、重複しても二度merge・revertしないことが重要です。

**3. 私なら、停止条件を変えずに先に試す**

最初の導入は次の形を勧めます。

1. ベンチ終了時、今回のrunに結び付いた事実の要約をMonitorへ送る。
2. mainは採否と短い根拠を記録する。通常時は「観測事実・判断・未確認点」程度に限定する。
3. 採否の投稿への同期、依存投稿の除外、revert、次候補の再確認、mergeを決められた順序で行う。
4. 次のベンチを起動する。
5. 起動後、前runの詳しい分析を最初の作業にする。

これなら、現行isuscopeの停止条件のままで時間短縮を測れます。例外として、通知だけでは採否を決められないrunは追加で読みます。今のmain手順にも、その例外は明記されています。[main.md:53](/Users/nao/project/isucon/isu-scaffold/.claude/commands/main.md:53)

手順3を専用コマンドにするなら、**採否と次候補はmainが渡し、コマンドは順序・対象commit・状態の整合性を検査する**構成がよいです。途中失敗から再実行できるよう、採否記録済み／revert済み／merge済みを区別します。

hookだけで吸収する案は、通知と冪等な同期には向きます。しかし操作順序の正本にするのは勧めません。現行hookはコマンド文字列から処理を選び、ベンチを含むと分析後処理を実行しません。新しいwrapperの内部も自動的には認識しません。[bench.rs:29](/Users/nao/project/isucon/isu-scaffold/tools/isu-hook/src/bench.rs:29)、[guard.rs:610](/Users/nao/project/isucon/isu-scaffold/tools/isu-hook/src/guard.rs:610)

将来的に1回のbackground呼び出しへまとめること自体は可能です。その場合は、**wrapper内でmerge完了後に測定対象を確定する**必要があり、今の「Bashから戻った瞬間にhookが測定中にする」責務を移す設計変更になります。

**4. 詳しい分析の必須化と、モデルの動きに関するリスク**

提案の停止条件は、未完了の分析を最大1run分までに制限する方向として合理的です。ただし、保証するのは「後続runを止める」ことであって、「起動20秒後に分析が届く」ことではありません。

主な懸念は次です。

- **書くのを忘れたままN+1が終わると、N+2の前に詳しい分析を書く。** データは残っても、短縮したかった停止時間が戻ります。
- **最後のrunは取り残せる。** 次の起動がないので、終了・freeze・セッション再開時の未完了検査が別に要ります。
- **文字数は分析品質ではない。** 完了状態を埋めるための定型文が増えても、改善には寄与しません。期待と実測、判断理由、不明点、次の検証先が残れば、短くても完了でよいと思います。
- **短い採否でimproveが動き出すのは、現行の指示どおりです。** [improve.md:69](/Users/nao/project/isucon/isu-scaffold/.claude/commands/improve.md:69)。速報で新しいボトルネックまで断定すると、20秒後の詳細で前提が変わり、手戻りが起きます。速報／詳細を明示し、速報では確認済みの採否根拠に絞るべきです。
- **キューが多いと、短縮対象以外の作業も増えます。** 衝突解消、部分採用、依存関係の整理、prebuild未実施の組み合わせが増えるので、供給が少なかった練習の29秒をそのまま本番へ外挿できません。

新状態を導入するなら、「最新の終わったrun」の定義、FAIL・中断・PENDINGの扱い、全投稿の採否完了、終了時の未完了解消まで契約に含める必要があります。さらに停止検査はdeploy前にも置くべきです。今の`bench.sh`では、isuscopeが未完了を理由に拒否する時点で、すでにdeployが終わっています。[bench.sh:36](/Users/nao/project/isucon/isu-scaffold/scripts/bench.sh:36)

**5. 速度見込みと導入順**

31回→37回という換算は、周回時間が本当に116秒→97秒になるなら妥当です。ただし、**10秒と詳細分析ほぼ100%は、まだ目標値**と扱うべきです。

現状でも短い分析で次へ進めるのに、実際には775字を書いています。通知改善だけでこの行動が変わる保証はありません。また旧hookの時間短縮分はすでに別変更で得られているため、効果を二重計上しない再計測が必要です。

本番に向けた優先順位は次です。

| 順位 | 入れるもの | 理由 |
|---|---|---|
| 1 | run ID誤転記、起動失敗時の`latest`、採否反映前mergeの問題を修正 | 高速化で誤った記録・構成を増幅させない |
| 2 | run ID付きの完了要約をMonitorへ配送 | 全周で発生していた最初の読取往復を直接減らせる |
| 3 | 短い採否記録と、順序を保証した採否反映・次候補取り込み | 現行isuscopeのまま主要な短縮を狙える |
| 4 | 人間の投稿が溜まった条件で再計測 | 独立投稿だけでなく、依存・衝突・部分採用を含める |
| 5 | 詳細分析の状態と、1runだけ後回しを許す停止条件 | 追記漏れが残るなら、完全性を保証するために追加する |

計測では停止時間の中央値だけでなく、遅い周回、採否訂正、誤った測定対象、詳細分析の遅延・未完了も見たいです。短縮して増えたrunが手戻りで消えていないかを確認できます。

全体の判断は **「直してから進める」** です。Monitorで事実を先に渡し、記述作業をベンチ中へ移す方針には賛成です。ただし、まず採否・投稿・runの対応と操作順序を正し、停止条件の変更は高速化とは分けて導入するべきです。
