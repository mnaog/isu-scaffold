fingerprint は、**ベンチの直前に、各サーバーが実際にどういう状態か**を記録した値の一覧です。isuscope が before collector として各nodeで `.isuscope/fingerprint.sh` を動かし、run に保存します。

記録しているのは次のものです。
- kernel と OS の版
- `nginx -T` の結果の hash（nginx の設定全体）
- MySQL の版
- 動いている systemd サービスの一覧の hash
- `fingerprint-paths` に並べたファイルや directory の hash。draft が、同期する item（アプリのバイナリ、設定、SQL、静的ファイルなど）から自動で作ります。

## 何に使われているか

1. **run の比較の前提**：`isuscope query --base` は、スコアの差の隣に「fingerprint のうち値が変わったもの」を出します（README:63）。たとえば nginx の設定の hash が変わっていれば、nginx の設定が変わったと分かります。
2. **同じ構成の再測定の拒否**：直前の run と比べ、identity、fingerprint、計測の設定のどれも変わっていなければ、isuscope はベンチを始めません。

## いるか

**仕組みとしては残し、directory を丸ごと hash する部分は外すのがよい、というのが私の判断です。**

- **安い部分は残す価値があります**：kernel、nginx の設定、MySQL の版、動いているサービスは、どれも一瞬で取れます。「deploy はしたが nginx の設定が想定と違う」「サービスが1つ止まっている」のような、git からは分からないサーバー側のずれを run の比較で見つけられます。
- **directory の hash は、ほぼ identity と重複しています**：scaffold の `identity_command`（`scripts/benchmark-identity.py`）が、deploy で配るファイルの commit 済みの中身をすでに比べています。このrepoでは「サーバー上のファイルを直接編集しない」決まりなので、配ったファイルが変われば identity 側で検出できます。directory の hash で新たに分かるのは、決まりに反した手作業の変更くらいです。
- **directory の hash は遅くなりえます**：静的ファイルが数百MBある問題では、毎回のベンチの前に、全nodeでそれを読み直します。

## 変えるならこうする

- `configure-draft.py:548` が作る `isuscope_fingerprint_paths` を、アプリのバイナリと systemd の unit ファイルだけに絞る。同期する directory は入れない。
- そうすれば、`fingerprint.sh` の新旧の違い（directory を hash できるか）は実質的に効かなくなります。前回挙げた3番目の問題は、影響がほぼなくなります。ただし、配布一覧（`config/scaffold-export.json`）への追加は、版を揃えるためにやっておくべきです。

fingerprint を丸ごと外すこともできます。その場合、再測定の拒否は identity だけで判定され、run の比較から「サーバー側で何が変わったか」の欄がなくなります。失うものに比べて、外して得するものはほとんどありません。

## ベンチ出力のひな形（`c66a61a`）
試走中のセッションが手作業で数分かけていた手順を、1つの script にしました。

1. **`python3 scripts/benchmark-sample.py <run>`**：保存された出力のうち、結果を含みそうな行と、今の正規表現が読んだスコアと合否を表示します。何も変更しません。読み取りが違えば、`config/benchmark.env` の正規表現を直して見直します。
2. **`--apply --score N --pass true|false`**：次をまとめて行います。
   - 運営向けの行と adapter 自身の結果行を除き、参加者向けの行だけを sample として書き出す
   - sample の期待値を記入する
   - ベンチ条件の記録（contract）を確定し直す
   - `--check` を通す
   - 判定保留の run なら `isuscope rescore` で確定する

`--score` と `--pass` は、出力を自分で読んだ値を渡す形にしました。正規表現が読んだ値で自動的に埋めると、正規表現が途中経過の数字を拾っていても検査が必ず通ってしまうためです。
