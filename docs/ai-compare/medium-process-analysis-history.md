## 共通条件と検証の確かさ

[環境の再現手順](medium-environment.md)を用意した。開始commitは全者 `15c18c7bf48070f11a28a6c03a91cfa1e5a6a070`、配布15ファイルのSHA256も一致する。元アプリはpractice-12の `3c551cb`。解答commitや過去の会話は渡していない。

Rust 1.63、同一Cargo.lock、offline vendor、4 jobs、独立したビルド済みtargetを使用。DockerやEC2は使わず、専用のローカルMySQL 8.0.33を使った。モデルは1者ずつ実行し、準備・operator監査の時間はCLI時間に含めない。

開始状態のcheck/test/mysqlは成功、追加acceptanceは登録直後の一覧SELECTが2件で失敗した。既知の修正をoperator専用コピーに適用し、4検証が成功する正対照も確認した。

独立監査ではoperator側のverifier・manifestを使い、保護ファイル、環境、commit、未commit変更を確認した。Codex/Claudeとも共通受入ファイルは変更せず、既存テストは許可した旧期待の更新以外に削除・弱体化なし。キャッシュ容量の変更もない。

CodexはDB不要テスト18件、Claudeは追加2件を含む20件が成功。両者とも既存MySQL結合テストと共通受入テストが各1件成功した。以下の対象は専用MySQLのCom_select差分で0件を確認した。

- 登録処理と、登録直後の所持品一覧。

## OpenCode / DS Flash：調査は進んだが、編集前に上限で終了

30ツール呼出し（read 16、bash 14）。cache、登録・受取処理、付与関数、DDL、ID生成、ログイン・強化経路、共通テストまで読んでいた。変更前に4検証を自分で実行し、既存3検証の成功と追加受入の失敗を再現している。

最後のイベントは `step_finish.reason = length`。この実験で引き継いだ設定は1応答の出力上限8,192で、ログではその応答のreasoning token数が8,193、通常outputが0だった。最終説明も編集もなく、初期commitのままで終了した。非公開の推論本文は分析対象にしていない。

CLI終了コードは0だったが、独立監査のacceptanceは101、結果commitもない。**プロセスの正常終了は仕事の完了を意味しない**という運用上の事例になる。

この結果は「DSでは実装できない」証拠にはならない。今回のmax推論と出力上限の組合せでは中難度を完了できなかった、という観測。上限を増やす再試行は別条件として扱う必要があり、今回は勝手に条件を変えて再実行していない。

検証を `| tail` で受けており、shellの終了コードでは失敗を見落としうる。ここではverifierが保存した実際の101で失敗を確認した。

## Codex / Astra：小さめの実装とDB障害経路の追加検証

14件のshellツール呼出し。複数の読取・編集・検証を1回へまとめるため、呼出し数だけで仕事量は比較できない。

実装前に、登録処理が生成したボーナス込みの行ではなく部分的なAPIレスポンスをcacheへ渡していることを説明した。登録成功時にレスポンスと全所持品を別々に返し、受取では書込結果を構造体へ保持して、transaction commit後に反映する方針を採った。素材が既知なら所持確認SELECTを省き、不明なら従来のDB経路を残している。

変更はRust 3ファイル、追加174・削除32、合計206行。既存DB結合テストへ約60行を追加し、次を自発的に確認した。

- DB接続が閉じていても、登録直後・受取後の一覧が返る。
- コイン・カードを書いた後、素材UPDATEをtriggerで失敗させても全体がrollbackされ、cacheが失効する。
- cards/itemsを不明にしたcacheで受取しても、不完全な情報を完全な所持品として扱わない。

本人の共通検証は4回とも成功。変更前の受入失敗を本人が再実行する手順はなかったが、環境準備では確認済み。diff確認・commit・clean確認も行った。

一方、cacheのカードや新素材を末尾へ追加し、DB側の読取順に揃える処理はなかった。これは共通fixtureでは露出せず、後述の追加監査で見つかった。障害時の整合性への検証は厚いが、異なる種類のデータと順序の組合せが抜けていた。

## Claude Code / Opus：並び順も扱い、単体テストを追加

17件のBash呼出し。登録時の全所持品保持、付与結果をcommit後に反映、未知の所持品を未知のまま保つ点はCodexと同様。素材増分と新規行を分けて返し、cache内の増加対象が見つからない場合は素材cacheを失効させる。

DDLのindexを読み、カードを `(card_id, deleted_at, id)` 相当、素材をitem_idで並べる実装を加えた。追加単体テスト2件では、完全な登録から受取までの反映、素材順、未知のcache、増加対象不一致時の失効を確認した。

変更はRust 3ファイル、追加233・削除19、合計252行。参考修正に近い規模だが、解答の差分一致は採点条件にしていない。

最初のcheckはE0308で失敗した。create_user_onceの戻り値をtupleへ変えた際、呼出側の `result => return result` が古い型のままだった。自分で修正して次のcheckから成功。途中で未導入のrustfmtを試し、失敗後は手作業で整形した。最後に4検証を再実行しcommitした。

多くの検証で `| tail` や `| grep` を使っているため、shell成功だけに頼る手順は改善余地がある。実際のverifier記録と独立監査では最終4検証の成功を確認できた。

最終回答でも、SQLにORDER BYがない以上、cacheの並びを現在のindex順へ寄せることと、将来のDB実行計画まで同じ順になる保証は別だと注意点を残した。

## 追加監査：配列順の差

これはCodexの完成差分を読んだ後に作った追加テストであり、当初全者へ配布した受入条件とは区別する。AIへフィードバックや修正依頼はせず、各成果物の別コピーで同じテストを実行した。テストは `config/ai-compare/medium_ordering.rs`、実行は `scripts/ai-compare/audit-ordering.py`。元の成果物・commitには手を加えていない。

登録時にcard_id=8のボーナスとitem_id=5の素材を持ち、その後にcard_id=2・item_id=3を受け取る。

| 経路 | カードのcard_id配列 | 素材のitem_id配列 |
| --- | --- | --- |
| DB経由 / 元コード / 参考修正 | `[2,2,2,2,8]` | `[3,5]` |
| Codexのcache経由 | `[2,2,2,8,2]` | `[5,3]` |
| Claudeのcache経由 | `[2,2,2,2,8]` | `[3,5]` |

元コード、参考修正、ClaudeはAPI/DBの比較が成功し、Codexは不一致で失敗した。SELECTにORDER BYがないので、これを一般的なSQLの順序保証や大会の採点規則違反とは断定しない。ただし、この固定環境でcacheの有無によって応答配列の順序が変わることは再現できた。採用前に順序の扱いを確認する必要がある。
