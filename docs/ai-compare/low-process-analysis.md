# 低難度タスクの解き方の比較

2026年10月1日に実行した3試行の、ツール呼び出し・出力・公開された説明・最終差分を比較した。3者とも同じ原因を特定し、2つのハンドラだけを修正して独立検証に合格した。今回の課題では最終成果物の品質差は見えず、調査範囲、操作のまとめ方、検証結果の扱いに違いがあった。

内部の推論過程は評価対象にしない。説明されなかった検討を「していない」とは扱わない。各1試行なので、以下はモデルの恒常的な性格ではなく、今回観測した行動である。

## 観測値

| 試行 | 完了時間 | ツール呼び出し | 修正前check | 修正後checkとtest | 検証コマンド内の合計時間 |
| --- | ---: | ---: | ---: | --- | ---: |
| OpenCode DS V4.1 Flash max | 48.12秒 | 19回 | 1回 | 各1回成功 | 11.30秒 |
| Codex GPT-6-Astra medium | 76.71秒 | 14回 | 1回 | 各1回成功 | 13.85秒 |
| Claude Code Opus 5.5 medium | 43.56秒 | 5回 | 2回 | 各1回成功 | 14.18秒 |

ツール回数はハーネスが公開する操作の単位。Claudeは1つのBashに複数コマンドを入れるため、5回を「作業が5個だけ」「他より調査が少ない」とは解釈しない。検証コマンド内の時間は `.local/validation.jsonl` のうち各CLI実行区間内の記録だけを集計し、独立auditを除いた。総時間との差分には他のツール、起動、hook、通信、推論、最終回答生成が含まれ、モデル応答待ちだけとは呼べない。

## OpenCodeとDS

1. Git状態と初期履歴を確認し、checkを実行。終了コード101とE0446を取得した。
2. `UserStore`の参照を検索し、型定義と2つのハンドラ周辺を読んだ。
3. ルート登録、モジュール宣言、他の公開関数、ハンドラの呼び出し元を確認した。さらにverify.pyとUserStoreの後半を読んだ。
4. 型の公開範囲を広げると戻り値の`Entry`にも影響する、と説明し、ハンドラの公開範囲を狭める案を選んだ。2つのEditで修正した。
5. checkとtestを別々に実行し、両方の終了コード0を確認。Git差分を確認して、対象ファイルを指定してcommitした。

**評価:** 問題箇所だけでなく、別案を採った場合の影響と利用箇所を調べてから変更している。局所修正として根拠が明確。公開関数一覧やテスト位置の追加探索は、この2行修正には広めだったが、総時間はCodexより短かった。ツール回数の多さを、そのまま遅さや非効率とは評価できない。

`AGENTS.md`を個別に読むツール呼び出しはJSONイベントにない。自動注入の有無までこのイベントだけで断定せず、明示的な読み取り回数とは分ける。結果の操作・差分からは、課題範囲の逸脱は観測していない。

## CodexとGPT-6-Astra

1. AGENTS.mdを明示的に読み、checkで終了コード101とE0446を取得した。
2. Git状態、Rustファイルと追加指示の配置を確認した。Git状態とファイル一覧の取得はstarted/completedイベント上で重なっている。
3. 型・モジュール・ハンドラの参照をまとめて検索し、該当ソースを範囲指定で読んだ。
4. 「crate内のルート登録から引き続き呼べる」と修正前に説明し、1つのパッチで2行を変更した。
5. check、test、`git diff --check`と差分表示を行った。git addとcommitを別操作で実行し、最後にGit状態と完全なcommit IDを確認した。

**評価:** 指示確認、失敗再現、参照関係、最小パッチ、検証、commit後の状態確認まで段階が明確。DSより狭い調査範囲で同じ結論に達した。今回の中で最も時間が長かったが、不要な修正や失敗した修正のやり直しはない。「迷ったため遅かった」とする根拠はない。進捗説明やGit操作の分割は観測できるものの、それぞれが何秒の差を生んだかは切り分けていない。

## Claude CodeとOpus

1. AGENTS.mdとTASK.txtを読み、同じBash呼び出しでcheckの出力末尾40行を取得した。
2. もう一度checkを実行し、今度はエラー部分をgrepで抜き出した。同じ呼び出しで型の参照検索とファイル一覧も取得した。
3. ハンドラ宣言、ルート登録、他ハンドラの公開範囲を1つのBashで確認した。
4. crate内からだけ使われるため公開範囲を狭める、と説明。1つのBashにsed編集、差分表示、check、testをまとめた。
5. Git状態を確認し、`git commit -qam`でcommitして短いcommit IDを取得した。

**評価:** 複数の独立・連続操作をまとめ、狭い範囲を読んで修正した。最短だった一方、出力表示を変えるために修正前checkを2回実行している。検証コマンドの合計時間は3者で最も長く、速さをビルド回数の少なさでは説明できない。

**検証上の注意:** check/testを`| tail`や`| grep`へ接続している。実際に修正前checkは終了コード101だったが、Claudeのtool_resultは`is_error: false`になっていた。コンパイル失敗は出力本文から認識しており、今回は修正後の実終了コードも0だったため、成功判定を取り消す理由にはならない。ただし同じ書き方を複雑な課題へ持ち込むと、失敗後も後続操作へ進む可能性がある。ログへ保存して終了コードを保持するか、pipefail等でパイプラインの失敗を扱う方が検証は確実になる。

また、commitはファイル指定のaddではなく`-a`を使用した。今回の試行はクリーンな専用リポジトリで差分も2行だけなので問題はなかった。共有された変更が存在する運用では、無関係な追跡済みファイルを巻き込まないか別途見る必要がある。

## 共通して確認できたこと

- 修正前に実際のコンパイル失敗を確認した。エラーを見ずに推測だけで直した試行はない。
- 全員が型の公開範囲を広げず、呼び出し元を確認した上でハンドラ2つを`pub(crate)`にした。
- 最初の修正でcheckとtestが成功し、修正後の手戻りはなかった。
- 依存関係・Rust・既存テスト・検証スクリプトの変更、不要なリファクタリングはなかった。
- 全員が実際にcommitした。operatorの独立検証では15 passed、1 ignored、クリーンなGit状態を確認した。
- 今回はエラー箇所がコンパイラから直接示される課題。設計力、DB整合性、広範囲の変更能力、難しい失敗からの回復力はまだ評価していない。

最初のOpenCode試行は起動先の指定不備で中止した。これはハーネスの失敗として記録済みであり、DSの探索能力や手戻り回数には加えていない。

## 中難度で観察する項目

| 観察対象 | 確認する具体的な行動 |
| --- | --- |
| 着手時の理解 | MySQLが正本であること、登録レスポンスが全所持品ではないことを把握するか |
| 調査のつながり | 登録・付与・受取・一覧取得・失効の関係を追い、必要な経路を取りこぼさないか |
| 実装前の判断 | SELECTを省ける条件と、省けない場合のフォールバックを根拠付きで定めるか |
| 整合性 | commit前にキャッシュを確定させないか、DB失敗・重複受取・同時更新・初期化を考慮するか |
| 変更の範囲 | 課題と無関係な容量変更や大規模リファクタリングを混ぜないか |
| テスト | 新しい動作を検証し、旧期待の更新と検証の弱体化を区別できるか |
| 効果の実証 | APIとDB結果を保った上で、対象SELECTが実際に減ったことを示すか |
| 手戻り | 初回検証の失敗をどう分類し、仮説を修正して収束するか。誤った修正を重ねないか |
| 完了判断 | 終了コードとログを確認し、未実行の検証や限界を正直に報告するか |
| operatorの負担 | 追加ヒント、手動修正、再実行、成果物の読み解きに何が必要だったか |

行数の多さや説明の長さ自体は加点しない。最終成果、検証の信頼性、手戻りと人間の介入を時間と併せて評価する。独立した採点用検証を用意すれば、今回のような出力の切り詰めがあっても自己申告だけで合格にせずに済む。
