# 中難度タスクの解き方と時間の比較

独自の出力上限を撤去したDS再実行を含めて比較した。DSは185.19秒、Astraは184.14秒で、時間差はほぼなかった。Opusは164.67秒。今回、DSの時間優位は出なかった。一方、約3分の大半をビルドに使ったわけでも、実装に行き詰まっていたわけでもない。

成果物は3者とも共通の4検証を通過した。ただし追加監査でDSとAstraの応答配列の順序に差が出た。Opusはこのケースも通った。速度と品質を合わせると、この1試行ではOpusの結果が最も良かった。ただし各1回、別ハーネス・異なる推論設定の比較であり、一般的なモデル順位を確定する結果ではない。

## 観測値

| 項目 | OpenCode / DS V4.1 Flash max | Codex / GPT-6-Astra medium | Claude Code / Opus 5.5 medium |
| --- | ---: | ---: | ---: |
| CLI開始から終了 | 185.19秒 | 184.14秒 | 164.67秒 |
| 共通検証実行時間の合計 | 14.99秒 | 16.31秒 | 22.46秒 |
| 共通検証の実行回数 | 13 | 4 | 10 |
| 公開されたツール呼出し | 60 | 14 | 17 |
| Rust差分（追加＋削除） | 289行 | 206行 | 252行 |
| 変更したRustファイル | 3 | 3 | 3 |
| 最終共通検証 | 全成功 | 全成功 | 全成功 |
| 追加の配列順監査 | 不一致 | 不一致 | 一致 |
| 実行中のoperatorによるヒント・修正 | 0 | 0 | 0 |

ツール回数は操作のまとめ方に依存する。Astra・Opusは1回のshellツールで複数ファイルの読取や編集・検証を行うため、60対14をそのまま能力差や仕事量の差とは扱わない。DSの再実行では設定を直したが、解答や追加監査の内容は伝えていない。

開始commitは全者 `15c18c7bf48070f11a28a6c03a91cfa1e5a6a070`、配布ファイルのSHA256も一致。固定Rust 1.63、offline依存、4 jobs、事前ビルド済みの独立target、専用ローカルMySQL 8.0.33を使用。モデルは直列実行し、準備・operator監査の時間を表から除いた。他の通常のMacプロセス負荷までは隔離していない。

## DSの185秒はどこで使われたか

OpenCodeのツール開始・終了時刻を集計すると、重複を除いたツール実行区間は **18.99秒**。残る **166.20秒** はツール実行区間の外だった。検証コマンド自体の14.99秒は、この18.99秒に含まれる。

残りにはモデル応答、通信、CLI、hook、記録されない処理等が含まれる。「推論に166秒かかった」とは断定しない。また、他の2者と同等に測れるツール区間データをこの分析では揃えていないため、この比率の横比較はしない。

| 開始からの時刻 | 観測した作業 | 区間の長さ |
| --- | --- | ---: |
| 0〜約72秒 | 指示・コード・テスト・DDLを読む。変更前に4検証。参照関係を再検索 | 約72秒 |
| 約72〜129秒 | cache、付与処理、登録、受取、テストを順に編集 | 約57秒 |
| 約129〜155秒 | check失敗を修正し、4検証を成功させる | 約26秒 |
| 約155〜185秒 | diff確認、4検証の再実行、commit、状態確認、最終回答 | 約30秒 |

これらは観測した操作で区切った経過時間であり、「調査中はコードだけを読んでいた」等の内部思考の分類ではない。

時間が伸びた要因として、次の行動が見える。

1. **最初の編集まで約72秒。** main.rs、cache、結合テスト、受入テストを読み、変更前の4検証も行った。調査・再現には意味があるが、すぐ書き始めた試行ではない。
2. **53応答に分けて作業した。** 編集は17回で、主に個別のread/editを順に呼んだ。編集ツール自体は多くが十数msなのに、次の編集まで2〜4秒程度の間隔がある。この間隔には次の応答生成等が入る。小さな処理のたびに往復する進め方が総時間へ効いている。
3. **長めの応答区間が2つある。** 約20.26〜39.50秒、51.21〜69.41秒の区間は計37.44秒。対応する応答のreported reasoning token数は8,949と8,032だった。内部推論本文は読んでいないので、何を検討していたかは断定しない。
4. **初回コンパイルの型エラーを1回直した。** 作成処理の戻り値を変更したが、呼出側のreturnが古い型のままだった。複雑な整合性バグで長く迷走した形ではなく、修正後は4検証とも通った。
5. **最後に同じ4検証をもう一度実行した。** 最初の4検証成功後、実装変更はなくdiff確認から再検証に進んだ。ただし再検証の実行時間自体は合計約1.23秒なので、ここを省いても大幅な短縮にはならない。

DSのreported reasoning token総数は25,665、通常outputは10,632。最後の応答のinputはcache hit込み123,833トークンだった。累積inputは約483万だが約470万がcache hitであり、同じ履歴を繰り返し含む数値である。「新しい情報を483万トークン読んだ」という意味ではない。広く読んで履歴を増やし、多くの応答で処理したという傾向は見えるが、これだけから通信待ち・prefill・生成の各時間や実課金は算出できない。

**解釈:** 今回のDSは、コンパイルが遅いというより、調査と小分けの操作を伴う53応答の作業全体に時間がかかった。「Flashなら課題完了も速い」とは限らず、応答速度とエージェントとしての完了速度は分けて測る必要がある。max推論の寄与を特定するには別試行が必要で、mediumへ変更すれば速くなるとはまだ言えない。

## DS：理解は正しく、慎重に実装したが順序を取りこぼした

1. AGENTS、TASK、verifierを読み、cacheとmain.rs、既存結合テスト・受入テストを確認した。
2. 変更前のcheck/test/mysql成功とacceptance失敗を自分で再現した。
3. 登録APIの部分的なレスポンスと、実際にDBへ書く全所持品を分ける `CreatedUser` を追加した。
4. 付与したカード・更新後素材・新規素材・コインを `GrantedItems` に保持し、commit成功後にcacheへ反映した。
5. cards/itemsの両方が既知の場合のみ所持確認SELECTを省き、不完全なcacheでは元の経路へ戻した。
6. 完全登録、容量超過、既存・新規素材等の反映を単体テストへ追加した。型エラーを修正し、検証・diff確認・commit・clean確認まで行った。

新しい実装でも世代・容量・guard破棄による失効を維持し、無関係な性能施策は混ぜていない。設計の主要部分は適切だった。再実行では検証を直接呼び、初回のようにtailで失敗コードを隠していない点もよい。

一方、カード・新素材を配列末尾へ足すだけだったため、異なる種類の受取を組み合わせた際の一覧順序が抜けた。追加単体テストも数量・件数中心で、この順序差を検出しなかった。

成果物は `418084d041259d019db263901deddd10d48e941c`。独立監査でDB不要テスト20件、既存MySQL結合テスト、共通受入テストが成功した。

## Astra：操作をまとめ、障害時の検証を厚くした

登録時の全行データをcacheへ渡し、付与結果をcommit後に適用する中心設計はDSと同じ。素材だけが既知なら所持確認を省くため、cards/items両方を要求するDSとは最適化の適用条件が少し違う。未知の成分を既知として扱わない点は維持している。

複数の読取やPythonによるまとめた編集をshellへ集約した。本人による変更前の失敗再現はなく、修正後の4検証を各1回実行。共通検証の途中失敗もなかった。それでも全体184.14秒でDSとほぼ同じだった。少ないツール呼出しだけでは完了速度を説明できない。

特によかったのは既存DB結合テストへの追加である。

- 登録後・受取後の一覧がDB接続なしでも返ること。
- コイン・カードを書いた後に素材UPDATEを失敗させ、全体がrollbackされcacheが失効すること。
- 不完全な所持品cacheではDBフォールバックを維持すること。

障害時の整合性に踏み込んだ検証だった。ただしDSと同様、末尾追加で配列順が変わることは取りこぼした。小さめの差分206行にまとまったが、差分が短いこと自体を品質の高さとは評価しない。

成果物は `da19e8da19c3c426cc784c3208b27d377a0af734`。独立監査でDB不要テスト18件とDBの2検証が成功した。追加したケースは既存の結合テスト内なので、テスト関数の個数は増えていない。

## Opus：順序を考慮し、限界も明示した

登録と付与の設計は他の2者に近い。付与結果は素材の増分と新規行を分け、増加対象がcache内で見つからなければ素材cacheを失効させる。

DDLのindexを読み、カードを `(card_id, deleted_at, id)` 相当、素材をitem_idで整列する処理を入れた。単体テスト2件では、登録から受取までの反映、素材順、未知の所持品、不一致時の失効を確認した。この観点が後の追加監査に効いた。

最初のcheckはDSと同じ種類の戻り値の修正漏れでE0308となり、自分で修正した。未導入のrustfmtを試して失敗する寄り道もあった。検証回数・検証時間はAstraより多いが、全体では約19.5秒短かった。

ただし検証をtail/grepへ渡す操作が多く、shell成功だけで判定する手順には改善余地がある。今回はverifierの実際の終了コードと独立監査でも最終成功を確認できた。

最終回答では「SQLにORDER BYがなく、index順へ寄せても別の実行計画で順序が変わる可能性がある」「元のfixtureではその違いを検証できていない」と限界を明示した。成功の主張だけで済ませず、未確認部分を報告した点を評価できる。

成果物は `bc22c63f2a1ddf3fe7a883ef2681b8ba1ab967d1`。独立監査でDB不要テスト20件とDBの2検証が成功した。

## 共通受入は通ったのに、追加監査で差が出た理由

当初のfixtureはカードが同一種類で、新しい素材も既存より大きいIDだった。末尾追加とDBのindex順の差が出にくい。この点はモデル側の検証不足だけでなく、operatorが用意した受入テストの不足でもある。

完成差分を読んだ後、card_id=8・item_id=5を登録時に与え、その後card_id=2・item_id=3を受け取る検査を別コピーで実行した。全者に同じ検査を使い、成果物へ修正やヒントは与えていない。

| 経路 | カードのcard_id配列 | 素材のitem_id配列 |
| --- | --- | --- |
| DB経由・元コード・参考修正 | `[2,2,2,2,8]` | `[3,5]` |
| DSのcache経由 | `[2,2,2,8,2]` | `[5,3]` |
| Astraのcache経由 | `[2,2,2,8,2]` | `[5,3]` |
| Opusのcache経由 | `[2,2,2,2,8]` | `[3,5]` |

これは当初の共通検証とは分けた追加監査。SQLにORDER BYがないため、大会の採点規則違反や一般的な順序保証違反とは断定しない。それでも、この固定環境でcacheの有無により応答配列が変わることは再現できた。DS/Astraを採用するなら、順序を仕様として扱うかを確認してから修正・検証する必要がある。

## 今回から判断できること

- DSもこの中難度を自力で実装できた。初回の出力上限による終了を能力不足として扱うべきではない。
- DSとAstraの約1秒差に意味のある順位は付けられない。Opusとの差約20.5秒も、1回だけでは安定した速度差とは言えない。
- この試行で確認できた範囲ではOpusが最も速く、追加監査にも対応できていた。AstraにはDB障害テストの厚さという長所があった。
- 3者とも正常終了・commit・共通テスト成功まで進めたが、それだけで成果物の互換性を保証できない。operatorの差分レビューと追加検証は必要だった。
- 次に速さを改善するなら、独立した読取のまとめ方、目的単位での編集、変更後の必要十分な検証を比較したい。これは未検証の改善仮説であり、出力を途中で打ち切る独自上限は追加しない。
- 低難度ではDSがAstraより約29秒速かったが、中難度ではその差が消えた。単純な局所修正の結果を、多段階の実装へそのまま外挿できない。

worker方針を確定するには、別タスクや同条件での反復が必要。今回は「DSを除外」でも「DSなら速い」でもなく、実装は可能だが、完了時間とレビュー負担を他の候補と同様に測るべき、という結果になった。
