初動の手順

準備からkickoffが終わるまでに、人間がすること。上から順に進める。

人間 AI（自動） 練習のとき 確かめること
開始の前日まで

1. 準備

問題を使わない道具・認証・作業場所をそろえる。問題のコードや配布物は、開始まで持ち込まない。

  1. 1

    大会用のrepoを作る

    人間

    isu-scaffoldのrootで、commit済みのscaffoldから独立したrepoを作る。

    python3 scripts/new-contest-repo.py <新しいdirectory> --github <owner>/<name>
    確かめる: GitHubのrepoがprivateであること。
    練習のとき: --practiceを付ける（practice.mdが残る）。config/tool-guard.jsonのcontest_keywordsに、練習する開催回の語を入れる。
  2. 2

    手元の道具をそろえる

    人間

    新しいrepoのrootで順に流す。

    ./scripts/ansible-install.sh --all
make isuscope-node
make builder-images
./scripts/fetch-observability-tools.sh
    確かめる: 4つとも成功すること。isuscopeを入れ直したらmake isuscope-nodeも流し直す。
  3. 3

    AIが動くことを確かめる

    人間

    Claude Codeにログインし、laneが使うclaude -pがconfig/lanes.jsonのmodelで応答するかを見る。問題の探索はしない。

    echo "Reply OK" | claude -p --model claude-opus-5-5 --effort high --permission-mode dontAsk
  4. 4

    ポータルにログインしておく

    人間

    chrome-debug（--remote-debugging-port=9222で起動したChrome）でポータルにログインする。ベンチの依頼とportalのセッションが、このcookieを使う。

    python3 scripts/portal-cookie.py --portal <ポータルのURL> --check
    確かめる: cookieの名前が出ること（値は出ない）。ポータルのURLをdocs/preparation/readiness.mdに書く。
    練習のとき: 開始の宣言の後に運営がpractice-portal/scripts/start.shを流すと、chrome-debugが選手としてログインする。
  5. 5

    作業場所を作る

    人間

    portal・improve・humanのworktree。開始と同時に、それぞれでセッションを起動する。

    make worktree BRANCH=portal PURPOSE="ポータルの情報とベンチ接続"
make worktree BRANCH=improve PURPOSE="継続的な改善（/improve）"
make worktree BRANCH=human PURPOSE="人間の作業場所"
  6. 6

    記録して閉じる

    人間
    • 手元のdiskの空きを確かめる（kickoffはlaneとbuildを同時に走らせる）。
    • docs/preparation/readiness.mdを埋め、未完了の項目には理由を書く。
    • commitしてpushし、git statusがcleanであること。
開始の直前

2. 構える

開始の時刻に、すぐ3つのセッションを起動できる状態にしておく。

  1. 1

    認証が生きているか

    人間
    • AWSの認証が通ること。切れていたら入り直す。
    • chrome-debugでポータルを開き、ログインが切れていないこと。
    aws sts get-caller-identity
  2. 2

    端末を3つ開く

    人間

    3つとも大会用repoのrootへ移っておく。ボードを見るブラウザも用意する。

    cd <大会用repoのroot>
開始から5分

3. 3つのセッションを起動する

人間が手を動かすのはここまで。あとはAIが役割ごとに進める。

  1. 1

    3つの端末で、それぞれ1行打つ

    人間

    役割の名前の付いたClaude Codeが、それぞれの作業場所で起動する。最初のcommand（/main・/portal・/improve）は自動で入るので、打たなくてよい。

     端末1 main
    $ make session ROLE=main
    → /main（自動） → ボードも起動
     端末2 portal
    $ make session ROLE=portal
    → /portal（自動）
     端末3 improve
    $ make session ROLE=improve
    → /improve（自動）
    確かめる: ボードがhttp://127.0.0.1:8765で開くこと。portが使われていたら、mainをBOARD_PORT=<別のport> make session ROLE=mainで起動する。
  2. 2

    mainに目標を渡す

    人間

    端末1（main）で/goalを打ち、目標を渡す。

    /goal 競技の終了までに、最終スコアを最大にする
  3. 3

    サーバーの起動はAIに任せる

    AI（自動）

    portalが当日マニュアルからサーバーの起動に要る情報を書き出し、mainがそれを見てサーバーを起動し、make kickoffを始める。

    練習のとき: 運営がstart.shを流した後、ポータルのサーバーリストのtemplateからstackを作る（それより前に作ったstackはポータルに登録されない）。ベンチ用のnodeは運営のものなので、接続先にはapp1〜3だけを書く。
5分〜初回ベンチ

4. kickoffを見守る

3つのセッションが並行して進む。人間は止めずに、ボードで進み具合を見る。

portal

  • サーバーの起動に要る情報を書く
  • ベンチの接続を作り、1回回して確かめる
  • 当日マニュアルなどの原文を保存する
  • ポータルの告知と質問への回答を見張る

main

  • サーバーを起動してmake kickoff
  • コードとschemaを先に回収（code-ready）。laneが7本走り出す
  • 全nodeを調べてdraftを作り、確かめて反映（完全import）
  • make first-benchで初回ベンチ
  • 初回ベンチを分析して記録（main analyzed）

improve

  • code-readyの後、コードとschemaを読む
  • 得点の仕組みと重い処理の見当をつける
  • mainの分析を受けて、最初の改善を作って投稿する

人間が見ること・呼ばれたらすること

見る

人間
  • ボード: kickoffの段階、ベンチのscore、作業中の投稿。
  • 各端末: AIから人間への問いかけが出ていないか。

伝える

人間
  • mainの端末へ直接打つ。
  • またはmake session ROLE=humanのセッションで「@mainに…と伝えて」。
こうなったら人間がすること
ポータルのログインが切れたchrome-debugでポータルに入り直す。
AWSの認証が切れた手元で入り直す（aws sts get-caller-identityで通ることを確かめる）。
手元のdiskが足りない不要なものを消して空ける。laneとbuildが同時に落ちる前に。
自分でも調べたい・直したいmake session ROLE=humanで人間の作業場所を開く。作り始めたらpython3 scripts/proposal.py working "<狙う制約と変更>"、できたらpython3 scripts/proposal.py submitでmainへ渡す。

mainの作業ツリーには触らない。deploy・ベンチ・remoteの変更はmainだけが行う（ほかから打つとhookが止める）。

初回ベンチの後

5. 初動の終わり

ここまで来たら初動は完了

  • ボードに初回ベンチのscoreが出て、mainの分析（main analyzed）が出ている。
  • improveが最初の改善を作り始めている。

以後は、improveが作って投稿し、mainが測って採否を決める流れが続く。人間は見守り、伝えたいことをmainへ伝える。終了前の手順は、人間がmainへ指示して始める（docs/guides/finish.md）。

手順の詳細はdocs/guides/preparation.md（準備）とdocs/guides/kickoff.md（kickoff）にある。
