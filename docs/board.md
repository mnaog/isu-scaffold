# ボード

`make board`で開く、人間が見るための読み取り専用の画面です（http://127.0.0.1:8765）。main worktreeのrootから開き、どのworktreeから開いても同じrunと記録を表示します。loopbackでGETだけを受け付け、計測・ベンチ・runの採否・ファイルは変更しません。Ctrl-Cで止めます。

画面に出すもの:

- スコアの推移と、選んだrunのスコア・仮説・分析・採否
- 比較元とのHTTP・SQLの比較、ホスト別の負荷、負荷走行の時系列、MySQL、APIの流れ
- 共有操作（ベンチ・deploy）の実行状況
- 作業中（main以外のimprove・human・worktreeが、いま作っているもの）と、ベンチ待ち（mainのベンチを待つ投稿のキュー）。ページの一番上
- 必ず残す記録（`config/records.json`の一覧と中身）

実装は`scripts/board/`、テストは`tests/test_board.py`と`tests/board-*.test.js`です。isuscopeはPATHの`isuscope`を使います。

## 記録

`config/records.json`に並べた必ず残す記録を、同じ順にカードで出す。カードには名前、残す時期（準備・kickoffなど）、置き場所、書く内容、更新時刻と最後のcommitを出し、まだ無いものは点線の枠で「未作成」、commitしていない変更があれば「未commitの変更あり」とする。開くと本文を出す。Markdownは見出し・段落・箇条書き・表・コード・引用・リンクだけを扱い、本文をHTMLとして解釈しない。外へのリンクはhttpとhttpsだけ、ほかの記録への相対リンクはボードの中で開く。JSONは整形して、それ以外の文字はそのまま出す。ディレクトリ（`docs/official/`）は中のファイルの一覧から開く。

読めるのは`config/records.json`の場所と、その中のディレクトリのファイルだけで、repoの外を指すsymlinkや`..`は読まない。1ファイル1MBまで。一覧は30秒ごとに読み直す（gitへの問い合わせは10秒に1回まで）。表示はmain worktreeの内容なので、worktreeで書いた記録はmainへ取り込むと出る。

## スコアの推移

画面は5秒、計測は30秒ごとに更新する。終了前のrunも実行状況用に保持するが、スコア推移と比較には終了runだけを使う。スコア推移はベンチスコアの直下に置き、表示runの選択とは独立した履歴として表示する。直近100件のrunのうち終了したrunを開始時刻順に等間隔で並べる。横軸は表示範囲内の実行順（FAIL・中断を含む）の等間隔とし、回数の数字は出さず日時だけを間引いて添える。件数が多い場合は横スクロールで点の間隔を確保する。PASSは折れ線、FAIL・中断は×印、スコア欠落は未取得欄に表示し、各点のツールチップで日時とスコアを確認できる。クリックまたは結果選択欄で選んだ結果のスコア・状態・日時・仮説は上部のベンチスコア欄にまとめ、run IDとcommitは右側の計測取得状況の下に常時表示する。スコア数値・状態・グラフはPASSを緑、FAIL・中断を赤、判定なしを中立色にそろえる。グラフ下に詳細を重複表示しない。ホバーだけでは選択結果を変えない。上部のスコア欄に差分は置かない。

各runには、そのrunを始めた時点までに同じ構成を2回以上測った組（`isuscope run --repeat`）から求めた誤差（得点の平均に対する標準偏差を、組をまとめて求めたもの）が付く。最新・選んだrunのスコアの横に1σを出し、推移の図にはPASSの線に沿って±1σ（濃）と±2σ（薄）の帯を描く。構成は各runの`identity`（配ったファイル、計測設定、waitの表など）で分ける。測り直しのrunは■、waitを試したrun（tag `wait`）は◆で描く。

## 待ちの表

APIごとの待ち（`ISUCON_WAITS`、`scripts/waits.py`）の、いまの表と、試した値の採否（IDが`wait-`で始まるisuscopeのchange）を並べる。

## 比較と詳細

通常は最新の終了runを自動表示する。グラフの上の「表示する計測結果」で日時・スコアから結果を選ぶ。「前の結果」「次の結果」で直近100件内の終了runを移動し、「最新に戻る」で自動表示に戻れる。結果の選択と移動は左側に常時表示し、比較元・サーバー・取得件数はその下の「比較・表示設定」に折り畳む。スコアの点のクリック／Enter／Spaceでも表示runを切り替える。「比較元」は「分析の比較元に追従」を既定にし、選択runの保存済み分析にある`base_run_id`を使う。未分析または比較元未記録なら比較なしとし、前回runや採用runを推測しない。画面で任意の比較元または「比較なし」へ変更でき、run移動後も手動選択を保つ。選択はそのタブだけの閲覧状態で、設定や採否は変えない。

スコア・HTTP・SQLを比較元／対象／差分／変化率で表示し、仮説・分析・変更の採否・計測commitも確認できる。試したこと（仮説）と分析状態を常時表示し、分析本文と採否は折り畳む。手動の比較元が保存済み分析の比較元と違う場合は、折り畳みの外で違いを明示する。採否は関連する変更の現在の判断で、当時の判断やdeploy済みを意味しない。HTTP・SQLの回数と平均時間は「比較元 → 対象」を同じ行に表示し、列見出しで対象の値をソートできる。片方だけにある行、欠測、比較元が0で変化率を算出できない値は0で補わない。

HTTPはrun全体、SQLは`--window load`のdigest単位。25／50／100件を取得し、列見出しのクリックで回数・合計・平均・p95・合計時間差分を並べ替える。ソートは取得済み行の範囲に限り、切り詰めは件数表示で知らせる。行を開くとHTTP status、SQLのロック時間・走査行数などを表示する。長いSQLはisuscope側の出力上限で省略される場合があり、digest IDとともに明示する。

詳細取得は最大2MB/コマンド、30秒のキャッシュ（最大8選択）を使う。再取得ボタンもキャッシュ有効期間内は同じスナップショットを返す。自動取得は約30秒ごと。

## 負荷の分析

選択runの`brief --limit 25`からホスト別CPU・コア・PSI・memory・service、upstream、クライアント接続、CPU上位関数、collectorの取得状況を表示する。HTTP/SQLと同じ画面で、`series --window load --bucket 5`による負荷走行の時系列とMySQLステータスを自動表示する。概要時系列は最大1000行、MySQLは指定9 metric・最大3000行。独立した読み取りは並列化し、既存の30秒キャッシュを使う。追加collectorやベンチは起動しない。

グラフの横軸は負荷走行開始からの秒数。要求数・SQL回数は毎秒レートではなく区間内の件数、HTTP p95は区間内の分位値の最大として表示する。欠測点は0で補わず、欠落区間を線で結ばない。load区間を取得できない場合はその欄へエラーを表示し、wholeへ自動で置き換えない。

「APIの流れと処理時間」は未計測時に実測と明確に区別したサンプル図と、計測後に表示する案内を出す。ユーザー遷移は固定の読み取り専用SQLで最初にPASSしたsurvey-runを探し、その`brief --limit 200`から最大80遷移をSVGの接続図で表示する。循環・自己ループを含め、接続関係で段を分ける。ノードには選択runのHTTP計測（最大500行）から、node別の回数・平均・p95・合計時間・エラーを重ねる。バーはAPIごとの最大サーバー合計時間を、図全体の最大値に対して表示する。ノードをクリックするとHTTP詳細を開ける。未取得は0扱いせず、図にないAPIは別表へ出す。初回の遷移回数は既定で表示し、線幅も回数に応じて変える（表示中の最大値を基準に1〜6px）。回数ラベルは設定で非表示にでき、通常runの遷移回数とは混同しない。図はオフラインで描画し、同じ接続のMermaidソースも保存できる。直近100件より古いsurveyも対象とし、参照runを明記する。遷移は毎runのisuscopeにも残る（runどうしの比較は`isuscope query --view transitions`）。isuscopeの遷移解析は`msec - reqtime`で開始時刻を求める。`transition.*`の品質metric（最大1000行）で重複実行・同時刻・旧形式を判別し、順序が曖昧な矢印は破線にする。品質metricのない既存surveyはすべて破線とする。実線も観測順であり、因果順序とは扱わない。cache HIT/MISSは現行の標準計測にはないため、表示値を推定しない。

## 画面の構成

スコア推移、run・分析、シナリオ、ホスト、時間軸、HTTP、SQL、MySQL、upstream、CPU、計測欠落、ベンチ走行履歴を一ページに表示する。タブによる表示切り替えは行わない。ページ内リンクの見出し列も設けない。普段読むデータを主に置き、低頻度の操作は結果選択の下の「比較・表示設定」にまとめて折りたたむ。見出しは表示内容を具体的に表し、比較条件・集計範囲・欠測など解釈に必要な情報は残す。閾値による自動解釈や「次に確かめること」は表示しない。
取得コマンドと計測の元データは画面に表示せず、取得時にブラウザの開発者コンソールへ`console.debug`で出力する。

HTTP・SQLは合計時間順の表を基本とし、重複する並べ替えボタン列を置かない。列見出しで並べ替え、API・SQL名から詳細を開く。HTTPのエラー数、SQLのロック時間・走査行数/回は常時表示する。API図は曲線と余白で流れを示し、未計測の表示例は大きく明示する。拡大率・遷移回数・保存は図の表示設定にまとめる。

対象run・比較元・node・取得件数を共通の表示条件とする。node指定は取得済みのHTTP/SQL・ホスト・時系列・CPU等を絞り込む。スコア・採否・計測欠落はrun全体のまま。サーバー側の取得上限を超えた行は検索・ソート対象にならない。

時間軸のサーバー凡例は各図の右上に置く。時間軸はカーソルまたは左右矢印で同じ経過秒を照合する。表示bucketの半幅より離れた値・欠測値は未取得とする。時間範囲での再集計は行わない。ベンチ走行履歴では状態と分析を別列にし、PASSは緑、FAIL・中断は赤で表示する。文章の列は見出しと本文を左揃えにし、終了runを選択して詳細を確認する。シナリオ群別のセッション集計、cache HIT/MISS、詳細flamegraphは表示しない。

HTTP・SQLの合計時間と差分を視覚的に強調する。差分の色は増減のみを表し、改善・悪化を自動判定しない。未取得グラフはコンパクトに表示し、取得値のあるグラフの面積を確保する。

## 作業中

ページの一番上に、main以外（improve・human・`make worktree`）が`python3 scripts/proposal.py working "..."`で宣言した作業を、始めた順に並べる。各行に、worktreeの名前（improveならimprove）・branch・何をしているか・始めてからの時間を出す。投稿（`submit`）か`working --done`で消え、worktreeが無くなったものは出さない。`.local/proposal-state/working/`を読むだけ（`scripts/board/proposals.py`）。

## ベンチ待ち

ページの一番上に、mainのベンチを待つ投稿（`scripts/proposal.py`）を、測定中・次のベンチ（merge済み）・待ち・保留の順に並べる。見出しの数はキューの待ち（測定中と保留を除く）で、improveが投稿できるのはこれが1件以下のとき。各行に、branch・投稿者（improveか、それ以外のworktree）・commit・仮説・期待する観測・投稿からの時間（測定中なら測定開始からの時間）・根拠のrun・積んでいる投稿・衝突・保留の条件を出す。freeze中はそう出す。`.local/proposals/`を読むだけで、gitを呼ばず、ファイルを書かない（`scripts/board/proposals.py`）。表示はmainが最後に記録した状態なので、衝突（`needs-sync`）はmainがベンチの起動か`pending`・`sync`で確かめたときに更新される。

## 実行状況

画面上部には、選択runとは独立した現在の共有操作、直近の終了ベンチの分析状態、deployの最終記録と最後に成功したdeployのcommitを小さく表示する。`.local/operation.lock/lock`が実際に保持されていることを非ブロッキングで確認し、`owner`に記録された操作と開始時刻を表示する。ownerファイルだけでは実行中と判定しない。lockファイルは作成・削除しない。

deployの段階と時刻は`.local/deploy-transactions/`、最後に成功したdeployは`.local/current-deploy-commit`から読む。記録は実環境との一致確認を意味しない。未終了runが残っていても、対応するベンチの共有操作を確認できないときは実行継続未確認と表示する。実行記録は5秒、ベンチ情報は30秒更新で、AIの思考中・実装中・残り時間は推測しない。
